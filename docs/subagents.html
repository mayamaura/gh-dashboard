サブエージェント構成

作業を誰に振るか。仕様が表として確定している作業は安いモデルへ、判断が要る作業だけ高いモデルへ振り分ける。定義の実体は .claude/agents/*.md。

ドラフト版 0.1更新 2026-09-08原本 docs/source/subagents.md

1. 考え方

このリポジトリの作業は、仕様がどれだけ確定しているかで 3 つに分かれます。

種類例振り先
参照・転記 — 答えがドキュメントに書いてある要求 ID の本文を引く、traceability を埋めるHaiku
確定した仕様の実装 — 期待値が表になっている純粋関数とテスト、UI、IO を伴う RustSonnet
判断 — 何が正しいかを決める必要があるOQ の結論、差分インデックスの設計、ADROpus

「タスクに落とせる」= 期待値が表になっているということです。この計画では テスト戦略 2 節の期待値表と 実装計画 のタスク行がその役割を果たしているので、多くの作業を Sonnet に渡せます。

2. コスト

Anthropic API の公表レート (100 万トークンあたり)。入力・出力とも同じ比率なので、比率だけ覚えれば足ります。

モデル入力出力Opus 比コンテキスト
Claude Opus 5$5.00$25.001.01M
Claude Sonnet 5$2.00$10.000.41M
Claude Haiku 4.5$1.00$5.000.2200K
注意

Haiku 4.5 は effort パラメータを受け付けません (400 が返る)。Haiku 系のエージェント定義に effort を書かないこと。また 200K しかないので、Haiku にはファイル全体を読ませる仕事を振らない — spec-lookup が grep で当たり行の周辺だけを読む設計にしてあるのはこのためです。

一番効くコスト削減は、モデル選択ではなく「読ませない」こと

docs/source/requirements.md は 77KB、生成後の HTML は 115KB あります。要求 ID を 1 つ確認するためにこれを親の文脈へ載せると、以降そのセッションの全リクエストが重くなります。

spec-lookup (Haiku) はこれを避けるためだけに存在します。数行を返すのが仕事で、その数行のために親が 115KB を抱え込まずに済みます。モデルを 1 段落とすより効きます。

3. 8 体の構成

定義は .claude/agents/<名前>.md。

エージェントモデルeffort役割ツール
spec-lookupHaiku—要求 ID / ADR / OQ / タスクの本文と根拠を引く読取のみ
docs-syncHaiku—traceability・実装計画の状態更新、docs:build編集可 (docs/source のみ)
probe-writerSonnetmedium段階 0 の読み取り専用プローブを書いて回し、数字を出す編集可
pure-fnSonnetmedium純粋関数 + ユニットテスト編集可
rust-ioSonnetmediumIO を伴う Rust (段階 1〜3)編集可
ui-implSonnetmediumReact + TypeScript の画面編集可
invariant-reviewSonnethighINV-1〜10 と規約違反の検出読取のみ
core-criticalOpushigh中核ロジックと設計判断、OQ の結論編集可

invariant-review だけモデルは Sonnet のまま effort を high にしています。見落としの代償が大きい (INV 違反は「動いていても差し戻し」) 一方、探すべきものは列挙済みなので、モデルを上げるより思考を厚くするほうが費用対効果が高いためです。

4. どれに振るか

やること振り先
「FR-C-24 は何を要求している?」「この判断の ADR はあるか」spec-lookup
T-0.2〜0.6 (プローブを書いて数字を出す)probe-writer
OQ の結論を出す / ADR を書くcore-critical
T-1.1〜1.2、その他の純粋関数とテストpure-fn
T-1.4〜1.7、T-2.1〜2.7、T-3.1〜3.7rust-io
T-1.8〜1.10、T-5.6〜5.14、T-6.8〜6.9、T-7.1〜7.14ui-impl
T-4.x (差分インデックス)、T-5.1〜5.5 (ライブ監視)、T-6.1〜6.7 (利用枠)core-critical
コミット前の不変条件チェックinvariant-review
実装が終わったあとの記録更新docs-sync

段階 4〜6 の中核が Opus なのは、要求に「こう壊れる」が名指しされているからです (FR-C-04 / 05 / 22 / 24〜26 / 51 / 86 …)。素直に実装すると踏むと分かっている罠が 16 個あり、そこを安く済ませても差し戻しで取り返せません。

5. 振らないほうがよい場合

サブエージェントは新しい文脈で始まるため、必要な前提を読み直す分の固定費がかかります。次の場合は自分でやるほうが安く済みます。

  • 1〜2 ファイルの小さな修正 (タイポ、定数の変更、import の追加)
  • すでに親が読んで理解している箇所の手直し
  • 前後の会話に強く依存する作業 (説明を書き起こす手間が実作業を上回る)

逆に、並行して進められる独立した作業が複数あるときは、まとめて振ると実時間で効きます。

6. 委譲するときの決まり

  1. 要求 ID を渡す。「いい感じに実装して」ではなく「FR-P-52 と FR-P-54 を実装。根拠は本文の引用を読むこと」
  2. 読むべきドキュメントを名指しする。全部読ませない (それがコストになる)
  3. OQ に依存する作業は、依存を明示する。未確定なら core-critical へ回すか、着手前に潰す
  4. 戻ってきた成果を invariant-review に通す。テストが緑でも、INV 違反はテストでは捕まらない
  5. 実装エージェントには実機確認まで求める (NFR-53)。「テストが通った」で受け取らない

7. 共通で守らせていること

全エージェントの定義に、それぞれの担当範囲に関係する不変条件を書き込んであります。とくに次は複数のエージェントに重複して書いてあります。

  • 取れない値を 0 や空文字で埋めない (NFR-40)
  • 区別できないものを UI で断定しない (FR-C-46 / NFR-42)
  • 依存を勝手に足さない (NFR-10 / 13) — 足したくなったら止まって相談する
  • 推測で埋めた箇所を必ず報告する — 黙って決めない

重複を嫌って 1 箇所にまとめないのは、サブエージェントが CLAUDE.md を読む保証がないためです。それぞれの定義だけで完結させます。
