2. データ取得の 3 系統

要求 4.2 の 3 系統は、実装上も別のモジュール・別の起動契機・別の永続化方針として分ける。混ぜた時点で NFR-03 が壊れる。

系統モジュール起動契機触ってよいもの永続化
(1) ライブcopilot::liveUI 側の 2 秒タイマー (タブ表示中のみ)小さなローカル状態ファイル / PID 生存確認 / トランスクリプト末尾のシーク読みしない (プロセス内メモリ)
(2) インデックスcopilot::indexerタブ表示・更新ボタン・自動 (未取り込みがあるときのみ、下限 10 秒)セッションログ全体の差分パース / DBする
(3) 利用枠copilot::quotaユーザー操作 + 長周期 (5 分以上)Copilot SDK / GitHub REST / DB (直近値)直近値のみ (+ 任意で時系列)
UI (2s タイマー) ──► live_status_get ──► ファイル読み + PID 確認 ── 数 ms UI (タブ表示) ──► index_refresh ──► バックグラウンドタスク ──► DB ──► snapshot イベント UI (操作/5 分) ──► quota_get ──► SDK ──失敗──► REST ──失敗──► 推定 ──► quota イベント

3. スレッドとタスク

実行文脈何を動かすか禁止
UI (WebView)描画・入力・2 秒タイマー重い計算
Tauri メインスレッドウィンドウ管理・イベント配送DB / 外部プロセス / ロック / ネットワーク (NFR-20)
非同期ランタイム (tokio)IPC コマンドの本体、git 呼び出し、SDK / REST 呼び出し長い同期ブロック
ブロッキングタスク (spawn_blocking)ディスク走査、差分インデックス、SQLite
dev サーバー読み取りタスク子プロセスの stdout / stderr を行読み

すべての #[tauri::command] は async fn とし、同期 IO は spawn_blocking に逃がす。AppState のロックを跨いで .await しない (デッドロックの定番)。

5. 主要な流れ

5.1 差分インデックス (FR-C-01..15)

index_refresh └─ 実行中フラグを立てる (立っていたら黙って return) FR-C-10 └─ spawn_blocking ├─ 対象ファイルを列挙 ├─ for each file: │ ├─ delta::decide(記録済みオフセット, 記録済みサイズ, 現在サイズ) │ │ → 継続 / 全再パース / 更新なし FR-C-06 │ ├─ オフセットからストリーミング読み (全体をメモリに載せない) FR-C-08 │ ├─ 改行で終わらない末尾断片を切り捨てる FR-C-05 │ ├─ 3,000 行ごとに: │ │ BEGIN │ │ turn_index に INSERT OR IGNORE (UNIQUE(file_path, byte_offset)) FR-C-07 │ │ sessions / subagent_runs / quota_events を更新 │ │ index_files.last_parsed_offset を更新 ← 必ずトランザクションの最後 FR-C-04 │ │ COMMIT │ │ 15ms スリープ (DB ロックを手放す) FR-C-09 │ └─ 進捗を 250-300ms に間引いて通知 FR-C-11 └─ 完了 → snapshot イベント (IR-44)

壊れた行は数えて読み飛ばす。読み飛ばした件数は UI に出す (NFR-43)。

5.2 ライブ監視 1 周期 (FR-C-40..52)

live_status_get (2 秒ごと / タブ表示中のみ) ├─ 状態ファイルを列挙 → PID 生存確認 → 死んでいる行を除外 FR-C-40 ├─ セッションごとに (パス, サイズ, mtime) を前回と比較 │ 同じならディスクを読まない FR-C-48 │ 違えば末尾 64KB をシーク読み (見つからなければ 512KB で 1 回だけ) FR-C-47 │ 末尾から遡って最初の本文レコードを採る FR-C-49 ├─ 稼働中サブエージェント "集合" を作る (ログファイルの mtime が 120 秒以内) FR-C-50 │ 件数は集合の長さとして導出する ← 別々に数えない FR-C-51 ├─ activity::synthesize(状態シグナル, 末尾レコード, 稼働中サブエージェント集合) FR-C-45 └─ 一覧から消えたセッションのキャッシュを剪定 FR-C-48

この経路にネットワークも外部プロセス起動も入れない (INV-4)。

5.3 利用枠の取得と降格 (FR-C-80..95 / 130..144)

quota_get(force) ├─ 下限間隔 (5 分) 内かつ force でなければキャッシュを返す FR-C-142 ├─ 経路 A: SDK account.getQuota │ 成功 → source = 実値(sdk) │ 失敗 → 理由を記録して B へ FR-C-136 ├─ 経路 B: GitHub REST (個人 / 組織の両方を試し、取れた方を使う) FR-C-140 │ 成功 → source = 実値(rest) ├─ 経路 C: インデックス済みトークンからの相対推定 (60 秒 TTL) FR-C-92/93 │ → source = 推定。UI に必ず「推定」と出す FR-C-82 └─ どれも不可 → source = 取得不可 + 「何をすれば取れるか」 FR-C-83

枠は独立に評価する。ある枠が実値で取れても、取れなかった別の枠に推定を混ぜない (FR-C-84)。

5.4 dev サーバーの生存管理 (FR-P-60..68)

アプリ起動時: Job Object を 1 つ作り、KILL_ON_JOB_CLOSE を設定 (platform/win_job.rs)
dev_start:    子プロセスを CREATE_SUSPENDED で起こす → Job に割り当てる → 再開
              stdout/stderr を行読みするタスクを 2 本 spawn
              URL を検出したら dev 状態を更新して projects-dev-status を発火
アプリ終了時: 明示的に全停止 → Job ハンドルを閉じる (取りこぼしを OS 側で回収)

ウィンドウを閉じただけ (トレイ常駐継続) では停止しない。終了イベントでのみ停止する (FR-P-62)。

6. 状態の置き場所

状態置き場所理由
スキャン対象フォルダ / 手動調整SQLiteユーザーの意思。消えては困る (DR-01)
セッション索引・集計SQLite一覧性のため (DR-03)
スキャン結果 / git 状態 / Copilot 利用状況プロセス内メモリ導出データ。永続化しない (DR-02 / FR-P-04)
dev サーバーのログメモリ上のリングバッファ 500 行DB に入れない (FR-P-64)
ライブ状況プロセス内メモリ2 秒で作り直す
インデックス進捗 / 最終取得時刻UI 側の appStoreタブ切替で消えてはいけない (FR-C-161)
タブ別スナップショットUI 側の appStore切替時に即描画するため (FR-C-164)

7. 失敗の扱い

失敗方針
1 プロジェクトの git 取得失敗その行だけ「git 情報なし」。全体は成功 (FR-P-43 / NFR-24)
1 セッションのパース失敗その行を読み飛ばし、件数を数えて UI に出す (FR-C-12 / NFR-43)
状態ファイルが読めない / 形式が変わった該当項目を空にして続行。機能全体を止めない (FR-C-13 / NFR-23)
SDK / REST の失敗経路を降格。直前の値と「取得できませんでした」を並べて出す (NFR-07)
未インデックスのセッション詳細エラーではなく null。「まだ記録がありません」と出し、1 回だけインデックスを起動 (FR-C-57 / IR-14)
dev サーバーの起動失敗状態を 失敗(理由) にする。他プロジェクトに波及させない

8. ログ

%LOCALAPPDATA%\gh-dashboard\logs\ に 5MB × 5 世代でローテーション (NFR-22)。不具合調査の起点はここに一本化する。 UI スレッドの応答性 watchdog (3 秒) の記録もここへ (NFR-21)。

ログにセッション本文・プロンプト・トークン値以外の内容を書かない。 パスは書いてよい (ローカルログのため) が、認証情報は当然書かない。
