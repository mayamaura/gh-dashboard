gh-dashboard ドキュメント

GitHub Copilot 稼働ダッシュボード / プロジェクトダッシュボード。Windows 常駐型デスクトップアプリ (Tauri v2 + Rust + React) の設計・実装ドキュメント一式。

状態: 設計完了 / 実装は段階 0 から更新 2026-09-12個人利用
最初に読むもの

実装に着手する前に 要求仕様書 の 0〜2 章と、CLAUDE.md の不変条件 INV-1〜10 を読んでください。この仕様書は珍しく「なぜその要求があるか」が全部書いてあります。理由を読まずに実装すると、要求どおりに書いたつもりで壊れます。

何を作るか

唯一の正 · 版 1.0
要求仕様書
FR-P / FR-C / DR / IR / NFR / OQ の全要求。実装判断に迷ったらここに戻る。元の Markdown からそのまま移管したもの。
着手前に実測
未決事項 (OQ)
OQ-01〜10 と、この環境での初期観測。OQ-02 と OQ-06 は設計の分水嶺 — 推測で埋めない。
画面
UI 仕様
2 タブの構成、各要素が表示するもの、そして「何を断定しないか」の文言ルール。

どう作るか

構造
アーキテクチャ
データ取得の 3 系統、スレッドの分担、モジュール構成、主要な処理の流れ、失敗の扱い。
永続化
データモデル
SQLite に置くもの / 置かないもの。全テーブルの DDL と、その列がなぜそうなっているか。
境界
IPC API 仕様
コマンド 19 種とイベント 7 種、主要 DTO。引数名のケース事故を防ぐ規約から始まる。
ADR
設計判断
Tauri を選んだ理由、チャートライブラリを入れない理由、statusLine を使わない理由。却下案も残す。
規約
コーディング規約
スタイルではなく「壊れ方を構造で防ぐ」ための規則。各項目に対応する要求 ID つき。

進め方

段階 0〜7
実装計画
要求 付録 C を、1 件ずつ着手できるタスク (T-0.1 …) に割ったもの。各段階の完了条件つき。
誰に振るか
サブエージェント構成
8 体の役割とモデル選択。仕様が表として確定している作業は Sonnet へ、判断が要る作業だけ Opus へ。
4 層
テスト戦略
純粋関数 8 つのテスト表、DB テスト、読み取り専用プローブ、そして実機確認チェックリスト。
対応表
要求トレーサビリティ
要求 ID → 実装ファイル → テスト。タスクを終えたらここを埋める。空欄は「未実装」の意味。
手引き
AI エージェント作業ガイド
最初の 5 分に何を読むか、迷ったときの判断基準、完了の定義。
語彙
用語集
同じものを別の名前で呼ばないための表。「紛らわしい対の区別」が本体。

この 3 つだけは常に

#不変条件根拠
INV-1Copilot 側のデータは読み取り専用。設定ファイルを書き換えないN-5 / NFR-32
INV-2認証情報を読まない・持たない・表示しない。DTO にフィールドすら定義しないN-6 / FR-C-72
INV-42 秒ポーリング経路にネットワーク・外部プロセス起動を入れないFR-C-42 / NFR-03

残る 7 つを含む全 10 件は CLAUDE.md にあります。これらに違反する変更は、動いていても差し戻し。

ドキュメントの直し方

docs/*.html が唯一の原本です。中間の Markdown は無く、このページ自体を直接編集します。判断の背景は ADR-0022 (旧 ADR-0008 を置換)。

ページを増やすときは docs/assets/docs.js の NAV に 1 行足します。このページ (docs/index.html) だけはカード配置のため手書きなので、カードも足してください。
