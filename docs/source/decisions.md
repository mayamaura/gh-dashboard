## ADR-0001 — デスクトップシェルに Tauri v2 を使う

**状態**: 採用

**文脈**: 常駐アプリとして軽量であることが要求されている (NFR-10)。ランタイム同梱や常駐サービス追加は設計判断の文書化を求められる。一方で、Windows の Job Object を叩く、数百 MB のログを差分パースする、といったネイティブ寄りの処理が要求の中心にある (FR-P-61 / FR-C-01)。

**判断**: Tauri v2 (WebView2) + Rust コアを採用する。

**理由**:

- Windows 11 は WebView2 を標準搭載しているため、ランタイムを同梱せずに済む。Electron は Chromium を丸ごと抱えるので NFR-10 に反する
- 差分パース・プロセスツリー管理・Job Object という要求の中心が、そのまま Rust の得意分野に重なる
- 要求 5.2 の種別判定リストで Tauri が 1 位に置かれている = 想定利用者が Tauri プロジェクトを日常的に扱う

**代償**: WebView2 のバージョン差でレンダリングが変わりうる。Rust のビルド時間が長い。

**却下した案**: Electron (NFR-10 に反する) / WPF・WinUI (図表の自前描画とレイアウト調整のコストが高い) / Web アプリ + ローカルサーバー (常駐の軽さとプロセスツリー管理に不利)

## ADR-0002 — 永続化は SQLite 1 本。導出データは持たない

**状態**: 採用

**文脈**: DR-01〜03。「何でも保存する」誘惑への予防線が要求として明示されている。

**判断**: `%LOCALAPPDATA%\gh-dashboard\app.db` の SQLite 1 本。置くのは「スキャン対象フォルダ」「手動調整」「セッションログの索引・集計」だけ。

**理由**: ディスクの現状を写しただけのデータを DB に持つと、「実体は消えたのに DB に残る」「リネームで別プロジェクト扱いになる」という同期ずれの世話が恒久的に発生する。一方で数百ファイルを毎回全走査してはセッション一覧すら描けないため、索引だけは例外として持つ。

**帰結**: プロジェクトスキャン結果・git 状態・Copilot 利用状況・dev サーバーのログは、すべてプロセス内メモリのみ。詳細は [データモデル](data-model.html)。

## ADR-0003 — セッション本文を複製せず、バイトオフセットで索引する

**状態**: 採用 (**2026-09-08、OQ-02 の実測で前提が成立。あわせて「自前索引を続けるか」を再判断した**)

**文脈**: FR-C-02。セッションログは数百 MB。実際に読み返されるのは「ビューアで開いた 1 レコード」だけ。

**判断**: 索引には `ファイルパス + バイトオフセット + バイト長 + メタデータ + 140 字プレビュー` のみを保存し、本文は開いた瞬間にシーク読みする。**`events.jsonl` を索引・集計・本文の唯一の正とする。**

### 前提は実測で成立した (OQ-02)

3 ファイル / 291,259 バイト / 77 レコードを走査した実測。

| 検査 | 結果 |
|---|---|
| 行数 / parse 成功レコード数 / parse 失敗 | 77 / 77 / **0** |
| BOM ありファイル | **0 / 3** |
| CRLF 行 | **0** |
| 末尾が改行で終わらないファイル | **0 / 3** |
| バイトオフセット往復検証 | **一致 77 / 不一致 0** |
| `--resume` 前後で先頭 133,394 バイトの SHA-256 | **一致** (既存部分は書き換えられない = 追記のみ) |

「生改行を含む行 22 件」はプローブの別項目で、**JSON としてはエスケープ済み**の文字列値のこと。行分割は壊れていない (parse 失敗 0 件が根拠)。

### なぜ `session-store.db` に乗り換えないのか

OQ-05 で `<COPILOT_HOME>/session-store.db` が **書き込み中でも読み取り専用で開けた** (12/12 成功、2〜4ms)。`assistant_usage_events` はモデル別トークン・`total_nano_aiu`・`agent_id`・`parent_tool_call_id` を持ち、**FR-C-20 の集計をほぼ肩代わりできる**。それでも索引の正を移さない。

1. **本文レコードが DB に無い。** 3 セッションで `turns` は **2 行**、`events.jsonl` は **77 レコード**。`checkpoints` / `session_files` / `session_refs` / `forge_trajectory_events` は **0 行**。加えて `turns` にはバイトオフセットに相当する位置情報が無く、FR-C-120 の「1 レコードだけシーク読み」が成立しない
2. **読み取り専用オープンの安全性を、測っていない条件まで広げられない。** 12/12 の成功はすべて **CLI が実行中 (= `-shm` を他プロセスが保持している)** 状態での測定。writer 不在で `-wal` が残った DB を開くと、SQLite は復旧のために `-wal` / `-shm` へ**書きに行くことがある**。それは INV-1 (Copilot 側に書かない) の違反になる。**不変条件を未測定の条件に賭けない**
3. **集計ソースを 2 つ持つと、FR-C-25 と同じ不安定さをセッション集計に持ち込む。** どちらを最後に処理したかで値が変わる。`events.jsonl` だけで `session.shutdown.data` の `totalNanoAiu` / `modelMetrics` / `agentMetrics` / `tokenDetails` が揃い、`totalNanoAiu / 10^9 = AI Credits` は 2 セッションで CLI フッター表示と一致した (0.38 / 0.6)
4. **壊れ方の粒度が違う。** `events.jsonl` は防御的パース (FR-C-13) で「その 1 行だけ落とす」に劣化させられる。DB はスキーマが変わるとクエリごと落ちる (`schema_version` テーブルが存在すること自体、変更が前提であることを示す)

**却下した案**:

- **`session-store.db` を索引の正にする** — 上記 1〜4
- **併用し、本文は `events.jsonl`・集計は DB から取る** — 上記 3。2 ソースの突き合わせコストに対して得るものが「既にログから取れる数字」しかない
- **レコード境界を別テーブルに記録する** — OQ-02 が成立したので不要。オフセットで足りる
- **`session-store.db` を起動時にコピーして読む (DR-05 の案)** — 本体 4,096 バイトに対し WAL が 609,792 バイト。**本体だけコピーしても中身が無い**

**帰結**: `session-store.db` の扱いは ADR-0013 に分離した。セッションのメタ情報 (cwd / エントリポイント / タイトル候補) は、DB ではなく **`session-state/<id>/workspace.yaml` (375 バイト)** から取る。`workspace.yaml` の `name` は初回プロンプトの本文がそのまま入るため、**140 字プレビューの上限を掛けて扱う** (INV-6)。

## ADR-0004 — ライブ監視のタイマーは UI 側に置く

**状態**: 採用

**文脈**: FR-C-41。「タブを離れたら確実に止まる」ことが要求。

**判断**: 2 秒タイマーは React コンポーネントの `useEffect` に置き、バックエンドには常駐ポーリングループを作らない。

**理由**: コンポーネントのマウント / アンマウントが「タブを見ているか」と厳密に一致する。バックエンドに置くと開始 / 停止の往復と状態管理が増え、「離れたら確実に止まる」保証がコードから読み取れなくなる。

**帰結**: 最小化の検知だけはネイティブ側から `window-visibility` イベントで送る必要がある (IR-46)。**WebView の `visibilitychange` は最小化で発火しない**ため。

## ADR-0005 — 図表は自前 SVG 描画。チャートライブラリを入れない

**状態**: 採用

**文脈**: FR-C-163 / NFR-13。ゲージ・ガント・系統図が必要。

**判断**: すべて自前の SVG + CSS で描く。アニメーションは GPU 合成されるプロパティ (`transform` / `opacity` / `stroke-dashoffset` / `filter`) に限定する。

**理由**: 必要な図は 3 種類だけで、いずれも汎用チャートライブラリの機能をほとんど使わない。常駐アプリのバンドルサイズとメモリに対して割に合わない。系統図とガントは**同じ木構築結果を共有する**必要があり (FR-C-114)、汎用ライブラリのデータモデルに合わせる方がむしろ制約になる。

**帰結**: アニメーション設定 (`自動 / 入 / 切`) を自前で持ち、`自動` は `prefers-reduced-motion` に追随する (FR-C-162)。

## ADR-0006 — DTO の型は生成せず、手で同期する

**状態**: 採用 (**再検討の余地あり**)

**文脈**: Rust の DTO と TypeScript の型を一致させる必要がある。`ts-rs` / `specta` のような生成器がある。

**判断**: v1 では生成器を入れず、`src/types/dto.ts` を手で書いて同期する。ただし**呼び出しは `src/ipc/commands.ts` の型付きラッパーに集約する** (IR-31)。

**理由**: 生成器はビルド手順と依存を増やす (NFR-10)。DTO の数は数十で、境界は 1 ファイルに集約されているため、手動でも破綻しにくい。

> [!注意]
> **この判断は IR-30 の事故 (`path_key` → `pathKey`) を防げない。**引数名のケース変換は型の一致とは別の問題で、生成器を入れても防げない。防ぐのは `rename_all = "snake_case"` の全コマンド適用と、ラッパー経由の呼び出しの 2 つ。
>
> DTO が 50 個を超えたら生成器の導入を再検討する。

## ADR-0007 — 状態管理ライブラリを入れず、小さな共有ストアを自前で持つ

**状態**: 採用

**文脈**: FR-C-161 / 164。長時間処理の進行状態とタブ別スナップショットは、タブ切替で破棄されてはいけない。

**判断**: `useSyncExternalStore` を使った 100 行程度の自前ストア (`src/store/appStore.ts`) を持つ。Redux / Zustand / Jotai を入れない。

**理由**: 共有したい状態は「インデックス進捗」「最終取得時刻」「タブ別スナップショット」「アニメーション設定」程度で、非同期の複雑な合成を必要としない。React 標準の `useSyncExternalStore` で足りる (NFR-13)。

## ADR-0008 — ドキュメントは Markdown 原本 + HTML 生成

**状態**: 採用

**文脈**: ドキュメント一式を HTML で提供する必要がある。一方で、手書きの HTML を十数枚維持するのは差分レビューにも AI エージェントの編集にも向かない。

**判断**: `docs/source/*.md` を原本とし、`tools/md2doc.mjs` で `docs/*.html` を生成する。生成物もコミットする (ビルドなしでブラウザから読めるようにするため)。

**運用**:

- 編集するのは **`docs/source/*.md` だけ**。`docs/*.html` を直接編集しない (次回生成で消える)
- `npm run docs:build` で再生成、`npm run docs:check` で生成物が原本と一致するか検査
- `docs/index.html` だけは手書き (カード配置のため)。ナビゲーションは `docs/assets/docs.js` の `NAV` に一本化

**代償**: 変換器が対応する記法の範囲でしか書けない。凝った記法が必要になったら、記法を増やすのではなく書き方を変える。

## ADR-0009 — 利用枠は「取れないこと」を一級の状態として扱う

**状態**: 採用 (**2026-09-08、OQ-06 の実測で補強。同日 T-0.8 で実測 2 点を訂正**)

**文脈**: FR-C-80〜95 / 130〜144。取得経路は A (SDK) → B (REST) → C (推定) と降格しうる。OQ-06 の実測次第では A が使えず B が主役になる。

**判断**: `QuotaSource` を `actual` / `estimated` / `unavailable` の 3 状態を持つ型として定義し、**枠ごとに独立して持つ**。`unavailable` には「何をすれば取れるようになるか」を必ず添える。

**理由**: 取れない値を 0 で埋めた瞬間、そのゲージは嘘になる (NFR-40)。「取得不可」はエラーではなく正常な状態のひとつ。

### 実測による補強 (OQ-06)

この判断は「念のため」ではなく、**実測で必要になった**。

- **経路 A が返す枠は `chat` / `completions` / `premium_interactions` の 3 つだけ。`ai_credit` という名前の枠は無い。** ただし **T-0.8 で訂正**: 3 枠には `entitlement` (付与額 200 / 2000 / 0) と `quota_reset_date` (`2026-10-01`) が付いており、**ゲージの分母とリセット日は経路 A で取れる** (`account.getCurrentAuth`)。`unavailable` から始まるのは「**アカウント全体の月次消費額を額で出す**」用途だけになった
- **`premium_interactions` は `entitlement = 0` かつ `has_quota: false` かつ `percent_remaining: 0`。** FR-C-131 は `-1` (無制限) を名指ししているが、実在したのは **`0` の方**であり `-1` は 1 度も観測していない。**適用外の判定は `has_quota === false` を第一基準**にし、`entitlement <= 0` は 0 除算ガードとして併用する。**`percent_remaining: 0` をそのままゲージに載せない** — FR-C-88 の `90% 以上 = 危険` に該当して、適用外の枠が真っ赤になる
- **型宣言 (`AccountQuotaSnapshot`) に無い `hasQuota` / `tokenBasedBilling` が実際には返る。** 型定義とランタイムに差がある。型に無いフィールドは次のバージョンで黙って消えうるので、**消えたら該当の枠だけ `unavailable` に落ちる防御的パースを前提にする** (NFR-23 / NFR-43)。どの API を使うかの判断は ADR-0017
- **[訂正] `resetDate` は「問い合わせ時刻に追従する」のではない。** 中身は**利用枠スナップショットの観測時刻**で、`getCurrentAuth().authInfo.copilotUser.quota_snapshots.*.timestamp_utc` と**ミリ秒まで同一**だった (SDK と REST を数秒差で別プロセスから叩いて確認: `2026-09-08T11:58:34.381Z` = `2026-09-08T04:58:34.381-07:00`)。同一プロセスで 3 回続けて呼んでも**値は動かない**。**リセット日として表示しない**結論は変わらないが、**理由が変わった**。本物の月次リセット日は `copilotUser.quota_reset_date` (`2026-10-01`)
- **観測時刻としては使えるが、鮮度 (FR-C-86) には足りない。** 「値が変化したときだけ更新される」保証が無く、**`quota_remaining` が 198.4 のまま `timestamp_utc` だけが 3 回動いた実例がある**。「この値が動いた = 利用枠が変わった」とは言えない。→ `observed_at` は**我々の側で「値が変わったときだけ」更新して持つ** (結論は据え置き、根拠を差し替え)

**帰結**: UI は 3 状態すべてに描画を持つ。「実値がある枠」と「推定の枠」を同じ画面に並べてよいが、**同じ枠の中で混ぜてはいけない** (FR-C-84 / 144)。枠ごとの取得経路の割り当ては ADR-0015。

## ADR-0010 — 単価・付与額・枠の名前をコードに埋め込まない

**状態**: 採用 (**2026-09-08、OQ-06 の実測で帰結を更新。同日 T-0.8 で「$ 表示を検討する条件」を訂正**)

**文脈**: 課金体系は 2026-06-01 に実際に変わっている (プレミアムリクエスト → AI Credits)。付録 A.4。

**判断**: モデル別の単価は `models.list` から実行時に読む (FR-C-134)。付与額・枠の名前も定数として持たない。

**理由**: プランとモデルの改定で必ず陳腐化する。埋め込んだ定数は、間違った金額を自信ありげに表示する形で壊れる。

### 実測: 単価が実行時にも取れなかった (OQ-06)

- **`models.list({})` は呼べたが、返ったのは `"auto"` 1 件のみで `billing` フィールドが無い。** FR-C-134 が前提にしている経路が、**この呼び方では成立しない**
- **`1 AI Credit = $0.01` の裏取り材料も得られなかった。** `getQuota` の戻り値に金額単位のフィールドは 1 つも無い
- 一方、**`totalNanoAiu / 10^9 = AI Credits` は実測で一致した** (382,635,000 → 0.38 / 598,806,000 → 0.6。いずれも CLI フッター表示と一致)

**判断の追記 (帰結)**: **単価が実行時に取れないなら、金額 ($) 換算を出さない。**

- 消費は **AI Credits 単位で表示する** (例: `0.38 credits`)。**$ に換算しない**
- FR-C-89 は「額も併記する」(例 `$6.20 / $10.00`) と書いているが、**その前提 (単価が取れる) が実測で成立していない**。要求本文は書き換えず、**OQ-06 / OQ-12 に「要求の前提が実測と異なる」として記録した**
- 単価が取れないことを「取れない」と表示する。**代わりに二次情報の $0.01 を掛けない** (INV-7 / NFR-40)

### [訂正] 「分母が経路 B で取れたら $ 表示を検討する」の前提が変わった (T-0.8)

訂正前は「**付与額 (分母) が経路 B で取れたら、その時点で $ 表示を検討する**」と書いていた。**前提が崩れた。**

- **分母は経路 B ではなく経路 A で取れる。** `account.getCurrentAuth` が `entitlement` (chat 200 / completions 2000 / premium_interactions 0) と `quota_reset_date` (`2026-10-01`) を返す (OQ-06 / ADR-0017)
- **それでも $ 表示は出せない。** 残る欠落は「**1 AI Credit が何ドルか**」の 1 点。`models.list` は `"auto"` 1 件で `billing` を持たず、`getCurrentAuth` にも金額単位のフィールドは 1 つも無い
- **`entitlement` の単位すら確定していない。** `chat` の消費区間 (1.55, 1.65] にローカル実測 1.5525 credits が収まり、`token_based_billing: true` とも整合するので AI Credits 建ての可能性は高いが、**1 アカウント・無料プラン (`free_limited_copilot`) の導出が 2 点あるだけ**。要求 付録 A.4 が言う「月額プラン料金と同額のクレジット」との対応は測れていない

**書き換え後の条件**: **$ 表示の条件は「単価が実行時に取れること」の 1 つに絞られた。** 分母が取れたことは条件を満たさない。分母が取れた今も、**AI Credits 単位で表示し、$ に換算しない**。

**却下した案**: `1 AI Credit = $0.01` を定数として持ち、注釈で逃げる — 注釈は読まれない。数字が出ている時点でユーザーはそれを信じる。**取れない値は出さない**方が常に安全 (NFR-43 / 44)。

**却下した案 (T-0.8 で追加)**: **`entitlement` を「$ 建ての付与額」とみなして額表示に使う** — 単位の裏取りが 1 アカウント・無料プランの区間一致 2 点しかない。`free_limited_copilot` の `entitlement: 200` を「$200」とも「200 credits」とも断定できない。**推定を実測として表示することになる** (INV-7 / NFR-40)。

**帰結**: 金額を出す日が来たら、**概算である旨を必ず添える (NFR-45)**。キャッシュトークンの扱いや端数処理まで一致する保証はない。**請求額の正は GitHub の課金画面。**

## ADR-0011 — `unsafe` / FFI は 1 ファイルに隔離する

**状態**: 採用

**文脈**: FR-P-61 / 68。dev サーバーのプロセスツリーを道連れで終了させるには Windows Job Object (`KILL_ON_JOB_CLOSE`) が要る。

**判断**: `src-tauri/src/platform/win_job.rs` にのみ `unsafe` を書く。他のファイルからは安全なラッパー越しに使う。`#![forbid(unsafe_code)]` を crate ルートに置き、当該ファイルだけ `#[allow(unsafe_code)]` で開ける。

**理由**: レビュー面積を絞る。「どこで OS を直接叩いているか」を探さずに済む状態を、構造で保証する。

## ADR-0012 — statusLine フックを使わない

**状態**: 採用 (**2026-09-08、OQ-04 の実測で再確認。判断は変わらない**)

**文脈**: Copilot の statusLine フックは `cwd` / `session_id` / `model` / `cost` / `context_window` を渡してくれる。

**判断**: 採用しない。**フック全般を使わない。**

**理由**: **statusLine には利用枠が載らない。**載っている情報はすべて SDK と差分インデックスで代替できる。採用すると「ユーザーの設定ファイル (`~/.copilot/settings.json`) を書き換える」「中継用の実行ファイルを同梱する」という対価だけが残る。

### 実測による再確認 (OQ-04)

`@github/copilot-sdk` の `dist/generated/rpc.d.ts` に定義されているフックイベントを実際に確認した: `sessionStart` / `sessionEnd` / `postResult` / `prePRDescription` / `errorOccurred` / `agentStop` / **`subagentStart` / `subagentStop`** / `preCompact` / `permissionRequest` / `notification`。

`sessionStart` / `sessionEnd` は FR-C-40 の稼働判定に、`subagentStart` / `subagentStop` は FR-C-24〜26 の完了ゲートに、それぞれ直接効きそうに見える。**それでも採用しない。**

- `subagentStart` / `subagentStop` が運ぶ情報は、`events.jsonl` の `subagent.started` / `subagent.completed` から**既に取れている** (OQ-07)。**追加で得られるものが無い**
- `sessionStart` / `sessionEnd` は稼働判定に効きうるが、代替が存在する (ADR-0014)。**代替がある限り、設定ファイルへの書き込みという対価は払わない**
- フックを入れると「アプリを消したのにユーザーの Copilot 設定に残骸が残る」というアンインストール時の負債も生む

**帰結**: 「Copilot 側のファイルは読むだけ」という不変条件 (INV-1 / N-5 / NFR-32) を例外なく保てる。**この ADR は不変条件を支える柱なので、覆すときは N-5 の再検討から始めること。**

**再検討の条件**: ADR-0014 の代替経路 (mtime + 末尾レコード) が実データで機能しないと判明し、かつ稼働判定が要求として外せないと確認できたときだけ。**そのときも N-5 の再検討が先。**

## ADR-0013 — `session-store.db` は集計に使わない。読むとしても補助・任意・最良努力

**状態**: 採用 (2026-09-08、OQ-05 の実測を受けて新規)

**文脈**: OQ-05 で、`<COPILOT_HOME>/session-store.db` が **CLI の書き込み中でも読み取り専用で開けた** (12/12 成功、2〜4ms、`journal_mode = wal`)。スキーマには `assistant_usage_events` があり、モデル別トークン・`total_nano_aiu`・`agent_id`・`parent_tool_call_id`・`initiator` (`user` / `agent` / `sub-agent`) を持つ。**FR-C-20 の集計をほぼ肩代わりできる形をしている。**

**判断**: **v1 では `session-store.db` を読まない。** 索引・集計・稼働判定のいずれの経路にも入れない。

**理由**:

1. **INV-1 を未測定の条件に賭けられない。** 12/12 の成功はすべて **CLI が実行中 (= `-shm` を他プロセスが保持している)** 状態での測定。writer 不在で `-wal` が残った DB を読み取り専用で開くと、SQLite は復旧のために `-wal` / `-shm` へ**書きに行くことがある**。それは「Copilot 側に書き込まない」の違反であり、**動いてしまった場合に気づけない種類の違反**
2. **必要な情報が、DB を開かずに取れる。** セッションと cwd の紐付け・エントリポイント・タイトル候補・更新時刻は、**`session-state/<id>/workspace.yaml` (375 バイト、プレーンテキスト)** に揃っている。`workspace.yaml` の mtime は `sessions.updated_at` と **10ms 以内**で一致した (3/3)。SQLite を開く理由が消える
3. **集計を 2 ソースから拾うと、FR-C-25 と同じ不安定さを持ち込む** (ADR-0003 の理由 3)
4. **INV-4 との相性が悪い。** 2 秒ポーリング経路で他プロセスが書き込み中の SQLite を毎周期開くのは、ネットワークでも外部プロセスでもないが、**待たされうる I/O** である。`workspace.yaml` の `stat` と `events.jsonl` の `stat` で済むなら、そちらが安い

**却下した案**:

- **`session-store.db` を索引の正にする** — ADR-0003 の 1〜4
- **`sessions.updated_at` を稼働判定に使う** — 動くことは確認した (再開でちゃんと進む。created 17:10:51 → updated 17:14:22)。だが `workspace.yaml` の mtime が 10ms 以内で同じ値を与えるうえ、**`sessions.updated_at` は最後のイベントより 4〜14 秒早い**。理由 1 の risk を払ってまで採る価値がない (ADR-0014)
- **起動時にコピーして読む (DR-05 の案)** — 本体 4,096 バイトに対し **WAL が 609,792 バイト**。本体だけコピーしても中身が無く、WAL ごとコピーすればサイズと整合性の両方を抱える
- **`turns` から本文を読む** — 3 セッションで **2 行**しか無く、`events.jsonl` の 77 レコードに対応しない。**本文の正ではない**

> [!注意]
> **INV-6 との関係を誤解しないこと。** `turns` には `user_message` / `assistant_response` の本文がそのまま入るが、**これは Copilot 側の DB であって我々の `app.db` ではない**。読むこと自体は INV-6 に触れない。INV-6 が禁じているのは**我々の DB に本文を複製すること**である。
> 一方 `workspace.yaml` の `name` (初回プロンプトの文面がそのまま入る) を**我々の DB に保存する場合は、140 字プレビューの上限が掛かる** (FR-C-02 / INV-6)。

**帰結**:

- 段階 4 は **`session-store.db` に一切依存せずに完成させる**。OQ-05 は「読めることは分かったが使わない」として **一部判明** のまま残す
- 将来 `events.jsonl` の形式が壊れたときの**代替経路の候補**として名前だけ残す。採用するときは、まず「writer 不在時の読み取り専用オープンが書き込みを起こさないか」を実測する

## ADR-0014 — 稼働中セッションの判定は `ide/*.lock` ではなく `events.jsonl` の末尾と mtime で行う

**状態**: 採用 (2026-09-08、OQ-04 の実測を受けて新規)

**文脈**: FR-C-40 は「**状態ファイル + PID の生存確認**」で稼働判定せよと書いている。OQ-04 の実測で、その状態ファイルが CLI セッションには存在しないことが分かった。

- `ide/*.lock` 3 件の `pid` は **すべて VS Code 本体 (`Code.exe`)** のプロセス ID
- **隔離 `COPILOT_HOME` で CLI を 4 回起動しても、`ide/` ディレクトリは 1 つも作られなかった**
- lock 側 PID 集合と `logs/process-*.log` 側 PID 集合の **交差は 0 件**
- `logs/process-*.log` には session id / workspace / cwd が **0 件**。5 件中 4 件は死んだ PID、生存 1 件もプロセス名が `Code` で **PID 再利用を排除できない**

**判断**: 情報源を役割で分割する。

| 情報源 | 役割 | 使わないこと |
|---|---|---|
| `ide/*.lock` | **FR-C-70〜72 の IDE ワークスペース一覧専用。** `pid` / `ideName` / `workspaceFolders` / `isTrusted` を読み、PID 生存確認で FR-C-71 の「切断済み」を出す | **CLI セッションの生死判定に使わない。`headers` は読まない (INV-2)** |
| `logs/process-*.log` | **使わない** | セッションを特定できず、PID も信用できない |
| `session-state/<id>/workspace.yaml` | セッション列挙 / `cwd` (FR-P-51 の `path_key`) / `client_name` (エントリポイント) / `name` (FR-C-54 のタイトル候補) | — |
| `session-state/<id>/events.jsonl` | **稼働判定の主経路。** (a) mtime が直近 N 秒以内 かつ (b) 末尾から遡って最初のレコードが `session.shutdown` でない | 中身の全読み。`session.shutdown` の**存在**だけを終了の根拠にしない |

**mtime の使い方の限定** (CLAUDE.md の mtime ルール / FR-P-56 / FR-C-50):

- mtime を使ってよいのは「**直近 N 秒に追記があったか**」の近似だけ
- **セッションの新旧・最終活動時刻は、末尾レコードの `timestamp` (中身のタイムスタンプ) から取る**。mtime で並べない
- FR-C-52 のとおり、**mtime 由来の遅れを UI で断定しない**

**`session.shutdown` を終了の確定シグナルにしない理由**: OQ-02 の実測で、**1 ファイルに複数現れた** (3 ファイルに 4 件)。`--resume` すると `session.resume` が後続し、その `parentId` が直前の `session.shutdown` の `id` を指してレコードの連鎖が続く。「shutdown が来たら終了」と扱うと**再開したセッションを永久に終了扱いする**。

**却下した案**:

- **`ide/*.lock` を稼働判定に使う** — CLI セッションと対応しないことを実測した
- **`logs/process-*.log` のファイル名 PID を使う** — セッションを特定できず、PID 再利用も排除できない
- **`sessions.updated_at` (session-store.db)** — ADR-0013
- **`sessionStart` / `sessionEnd` フック** — ADR-0012

> [!注意]
> **要求の前提が実測と異なる。** FR-C-40 の「状態ファイル + PID の生存確認」は、**VS Code 経路 (FR-C-70〜72) には成立するが CLI 経路には成立しない**。要求本文は書き換えず、OQ-04 に記録した。
> **測っていないこと**: CLI background / coding agent / VS Code 拡張の 3 経路は 1 度も動かしていない (`client_name` は `github/cli` の 1 値のみ観測)。N 秒しきい値 (FR-C-50 の目安 120 秒) の妥当性も未測定 — 観測できたずれは 4〜14 秒。**段階 5 の実機確認で「稼働中に見える / 終了後に消える」を通しで確かめる。**

## ADR-0015 — 利用枠の取得経路の優先順は「経路ごと」ではなく「枠ごと」に決める

**状態**: 採用 (2026-09-08、OQ-06 の実測を受けて新規。**同日 T-0.8 の実測で枠ごとの表と実装ルールを全面的に見直した**)

**文脈**: FR-C-130 と要求 6.8 は、取得経路を **A (SDK) → B (REST) → C (推定)** という**経路単位の一列の優先順**として書いている。OQ-06 の実測では、経路 A は**ある枠には実値を返し、別の枠には何も返さない**。一列の優先順のままだと「A が成功したから B に降格しない」と判断してしまい、**A が返していない枠が永久に埋まらない**。

**判断**: 優先順を「**枠ごとに、その枠を実値で返せる経路の中で最上位**」と読み替える。降格は**枠単位**で独立に起こる (FR-C-84 / ADR-0009 と同じ粒度)。

> [!注意]
> **T-0.8 (2026-09-08) で前提が 2 つ変わった。**
> 1. **月次の付与額 (分母) と本物のリセット日は、経路 B ではなく経路 A で取れる。** 経路 A の API を `account.getQuota` から **`account.getCurrentAuth`** に切り替える (ADR-0017)
> 2. **`resetDate` は「毎回変わる値」ではなく「スナップショットの観測時刻」だった。** 鮮度の扱いの結論は変わらないが、根拠が変わった (下記)

### 枠ごとの取得経路 (T-0.8 の実測で更新)

| 枠 | 実値の経路 | 実測 |
|---|---|---|
| `chat` / `completions` / `premium_interactions` の残率・付与額・残量 | **経路 A (`account.getCurrentAuth`)** | 3 枠とも `entitlement` / `quota_remaining` / `percent_remaining` / `has_quota` が返る。**B / C に降格しない** |
| 月次リセット日 | **経路 A (`copilotUser.quota_reset_date`)** | `2026-10-01` / `quota_reset_date_utc` = `2026-10-01T00:00:00.000Z`。**`resetDate` でも `quota_reset_at` (= 0) でもない** |
| 出所側の観測時刻 | 経路 A (`quota_snapshots.*.timestamp_utc`) | 3 枠とも同一値。**これだけでは FR-C-86 を満たさない** (下記) |
| セッション / ローカル合計の**消費 AI Credits** | **ローカル (`events.jsonl` の `totalNanoAiu / 10^9`)** | 2 セッションで CLI フッター表示と一致 (0.38 / 0.6)。**推定ではなく実値** |
| セッションのコンテキストウィンドウ使用率 | ローカル (`session.shutdown.data` の `currentTokens` / `conversationTokens` 等) | 4 レコードで観測 |
| **アカウント全体の月次消費額 (履歴つき)** | **経路 B (取得不可)** | 公開課金 API は 10/10 が 404。うち 5 件は `user` スコープ不足が真因。**`unavailable`** (OQ-12 / ADR-0018) |
| **組織 / Enterprise 管理下の枠** | **経路 B (未検証)** | 試行対象の組織が 0 件。FR-C-140 は 1 度も叩けていない (ADR-0018) |
| **モデル別単価 / $ 換算** | **取得不可** | `models.list` は `"auto"` 1 件で `billing` 無し (ADR-0010) |

### 枠ごとの実装ルール (実測から導いた、破ると壊れるもの)

- **`percent_remaining` (= `remainingPercentage`) を再計算しない。** **[理由を訂正]** 同じ消費が**丸めの異なる 3 つの値**で返るため。chat の実測で `entitlement − quota_remaining` = **1.6** / `entitlement − remaining` = **2** / `credits_used` = **1**。`percent_remaining` は**小数の `quota_remaining`** から算出されており厳密一致する (198.4/200 = 99.2)。整数丸めの `usedRequests` (= 2) から再計算すると 99.0% になり **0.2 ポイント**ずれる。**丸めの違いであって、単位不明でもバグでもない**
- **消費量を出すなら `entitlement − quota_remaining` (小数) を使う。** ゲージの率と同じ元データから出るのはこれだけ。**`remaining` / `usedRequests` / `credits_used` と混ぜない**
- **`usedRequests` を表示にも計算にも使わない。** **[訂正]** 「単位不明」ではなく `entitlement − remaining` (整数丸め) である。真の消費 1.55 が 2 に丸め上がる
- **適用外の判定は `has_quota === false` を第一基準にする。** `premium_interactions` は `percent_remaining: 0` を返すが、これは「残り 0%」ではなく「この枠は適用されない」。**そのままゲージに載せると FR-C-88 の `90% 以上 = 危険` に該当して真っ赤になる。** `entitlement <= 0` は 0 除算ガードとして併用する
- **無制限の判定は `unlimited === true`。** FR-C-131 が名指しする `entitlement = -1` は**1 度も観測していない**。実在したのは `0` + `has_quota: false` の方
- **`resetDate` をリセット日として表示しない。** **[理由を訂正]** 「毎回変わるから」ではなく、**中身がスナップショットの観測時刻 (`timestamp_utc`) だから**。SDK と REST を数秒差で別プロセスから叩いてミリ秒まで一致することを確認した (`2026-09-08T11:58:34.381Z` = `2026-09-08T04:58:34.381-07:00`)。同一プロセスで 3 回続けて呼んでも動かない
- **`quota_reset_at` を使わない。** 3 枠とも `0`
- **FR-C-85 (リセット後の観測を除外) は `quota_reset_date_utc` で判定する。** 観測時刻がリセット日時より前の期間のものなら、その観測を捨てる
- **FR-C-86 の `observed_at` は我々の側で持つ。** `timestamp_utc` は**出所の観測時刻としては正しい**が、「値が変化したときだけ更新される」保証が無い (`quota_remaining` が 198.4 のまま `timestamp_utc` が 3 回動いた実例)。**値が変わったときだけ `observed_at` を更新する**
- **「ローカル合計の消費クレジット」を「アカウント月次消費」として表示しない。** 前者は実値、後者は取得不可。**別の枠として持つ** (混ぜると下限値を全体値として見せることになり INV-7 違反)
- **枠の名前は API が返す `quota_id` をそのまま使う。** `chat` を「月次 AI Credits」と読み替えない (FR-C-134 / INV-7)

**却下した案**:

- **経路単位の一列の降格をそのまま実装する** — A が部分的に成功したときに、A が埋めなかった枠が永久に空になる
- **A で取れない月次 AI Credits を、ローカルの `totalNanoAiu` 合計で埋める** — 数字としては実測値だが、**アカウント全体をカバーしていない**。率にした瞬間に嘘になる
- **付与額をプラン名から定数で引く (Pro なら $10 等)** — ADR-0010。課金体系は実際に一度変わっている
- **`chat` 枠を「月次 AI Credits ゲージ」としてラベルし直す (T-0.8 で追加)** — `entitlement: 200` が AI Credits 建てである裏取りは、1 アカウント・無料プランでの区間一致 2 点しかない。**名前を変えて出した瞬間に、推定を実測として表示することになる** (INV-7)
- **`usedRequests` / `credits_used` を消費量として表示する (T-0.8 で追加)** — 真の消費 1.55 がそれぞれ 2 と 1 になる。率と整合しない

> [!注意]
> **要求の前提が実測と異なる (T-0.8 で更新)。**
> FR-C-130 は取得を `account.getQuota` に固定し、`resetDate` を「そのままゲージに載せる」項目に挙げているが、**`getQuota` は劣化射影であり、`resetDate` はリセット日ではない** (ADR-0017)。
> FR-C-89 の「額 ($) の併記」は単価が取れないため出せない (ADR-0010)。
> FR-C-138〜140 の経路 B は現行スコープで取れず、組織 / Enterprise は未検証 (ADR-0018)。
> **要求本文は書き換えていない。** 差異は OQ-06 / OQ-12 に記録した。**経路 B が `user` スコープで実測できたら、この ADR と ADR-0018 を更新する。**

## ADR-0016 — サブエージェント実行の主キーは `toolCallId` にする

**状態**: 採用 (2026-09-08、OQ-07 の実測を受けて新規)

**文脈**: FR-C-22 は「**主キーは親側と子側の両方に必ず存在する識別子**とする。片側にしか存在しない ID を主キーにしない」と要求する。OQ-07 で候補が 4 つ観測できた。

| 候補 | 件数 / 出現率 | ユニーク | 親側にあるか | 子側にあるか |
|---|---|---|---|---|
| **`toolCallId`** | 親の `tool.execution_start.data` と 子の `subagent.*.data` の双方 | — | **あり** | **あり** |
| `agentId` | 18 / 23.4% | 1 | **無し** | あり |
| `data.parentToolCallId` | 7 / 9.1% | 1 | — | あり (親の `toolCallId` を指す) |
| `data.parentAgentTaskId` | 5 / 6.5% | 5 | — | あり |
| `parentId` | 77 / 100% | 74 | あり | あり |

**判断**: **`toolCallId` を主キーにする。**

- 親側: `tool.execution_start.data.toolCallId` (`toolName: "task"` のもの)
- 子側: `subagent.started.data.toolCallId` / `subagent.configured.data.toolCallId` / `subagent.completed.data.toolCallId`
- 孫側: 子のツール呼び出しの `data.parentToolCallId` が親の `toolCallId` を指す (7 件で確認)

**却下した案**:

- **`agentId`** — **子側にしか付かない** (77 中 18 = 23.4%)。親の `tool.execution_start` には無い。FR-C-22 が名指しで禁じている「片側にしか存在しない ID」そのもの。加えて**拒否されたケースではサブエージェントが起動しないため `agentId` が存在せず、キーを捻出できない** (FR-C-22 の理由 (a))
- **`data.parentAgentTaskId`** — 5 件 / ユニーク 5。何と対応する ID なのかが分かっていない。**意味の分からない値を主キーにしない**
- **`id` / `parentId` の連鎖** — 100% 付くが、これは**レコードの木であってエージェントの木ではない**。1 レコード 1 ユニーク (77 件 / 74 ユニーク) で、実行単位のキーにならない
- **`session.shutdown.data.agentMetrics` のキー (`agentId`)** — セッション終了時にしか現れない。実行中の行を作れない (FR-C-23 が「起動を見つけた時点で行を作れ」と要求している)

**帰結**:

- FR-C-23: 親側の `tool.execution_start` (`toolName: "task"`) を見つけた時点で `toolCallId` をキーに行を作り、以降マージする
- FR-C-25 (完了通知は単一ソース): **`subagent.completed` のみを完了ソースにする。** `subagent.configured` にも `session.shutdown.data.agentMetrics` にも完了に見える情報があるが、**拾わない**。拾うと終了時刻が処理順に依存する
- FR-C-26 の 2 段階ゲートは `toolCallId` で照合する
- FR-C-27: 「拒否」と「失敗 / 中断」は**別の状態値として定義する**

> [!注意]
> **未確定を残したまま採用している。** OQ-11 のとおり、**拒否されたケースと非同期委任を 1 件も観測していない**。
>
> - 拒否時に `tool.execution_start` が書かれるのか、`toolCallId` が振られるのかが分かっていない。**書かれないなら FR-C-22 の理由 (a) が `toolCallId` でも解けない**
> - `mode` / `executionMode` は `sync` しか観測していない。**FR-C-24 が警戒する「起動しただけの暫定応答」の経路そのものが未確認**
>
> したがって **T-4.9 (完了ゲート) / T-4.10 (拒否と失敗の区別) は OQ-11 が埋まるまで着手しない。** FR-C-27 の「拒否」は**値としては定義するが、遷移させる経路を持たない**実装にしておく。**推測でゲートを組むと、直せない形で壊れる。**

## ADR-0017 — 利用枠の実値は `account.getQuota` ではなく `account.getCurrentAuth` から取る

**状態**: 採用 (2026-09-08、T-0.8 の実測を受けて新規)

**文脈**: FR-C-130 は取得を **`account.getQuota`** と名指ししている。T-0.8 で、同じサーバ側スナップショットを 2 つの API と 1 つの REST エンドポイントから取り比べた結果、**`getQuota` はそのスナップショットの劣化した射影**であることが分かった。

| 項目 | `account.getQuota` | `account.getCurrentAuth` | REST `copilot_internal/user` |
|---|---|---|---|
| 枠あたりのフィールド数 | **10** | **12** | **13** |
| 付与額 (分母) | `entitlementRequests` 200 | `entitlement` 200 | `entitlement` 200 |
| 残率 | `remainingPercentage` 99.2 | `percent_remaining` 99.2 | `percent_remaining` 99.2 |
| **小数の残量** | **返らない** | `quota_remaining` **198.4** | `quota_remaining` **198.4** |
| **月次リセット日** | **返らない** | **`quota_reset_date` `2026-10-01`** | 同左 |
| 枠が適用されるか | `hasQuota` (**型宣言に無い**) | `has_quota` | `has_quota` |
| プラン識別 | 返らない | `copilot_plan` / `access_type_sku` | 同左 |
| 観測時刻 | `resetDate` (**名前が誤り**) | `timestamp_utc` | `timestamp_utc` |
| 差分 | — | — | `credits_used` のみ追加 |

**判断**: **経路 A の実値取得は `account.getCurrentAuth` を使う。`account.getQuota` は使わない。**

**理由**:

1. **`getQuota` は必要な 2 つを落としている。** ゲージに要る**小数の残量** (`quota_remaining`) と**本物の月次リセット日** (`quota_reset_date`) が返らない。前者が無いと率と消費量の整合が取れず (`usedRequests` は整数丸め)、後者が無いと FR-C-85 の「リセット後の観測を除外」が実装できない
2. **`getQuota` は 1 つのフィールドを誤った名前で返す。** `resetDate` の中身はリセット日ではなく**スナップショットの観測時刻**である。SDK と REST を数秒差で別プロセスから叩き、`resetDate` = `2026-09-08T11:58:34.381Z` と `timestamp_utc` = `2026-09-08T04:58:34.381-07:00` が**ミリ秒まで一致**することで確認した。**間違った名前のフィールドは、読んだ人が正しく使う方が難しい**
3. **`getQuota` を使っても「型宣言だけに頼る」ことはできない。** `hasQuota` / `tokenBasedBilling` は**型に無いのに返る**。どちらの API を選んでも防御的パース (NFR-23) は必須であり、**`getQuota` を選ぶ理由が「型に載っているから」にはならない**

**型宣言の確認 (ADR-0009 の原則との関係) — 2026-09-08 に実測で解決**:

ADR-0009 は「**宣言されたフィールドだけを使う**」と書いた。`getCurrentAuth` 側がこれを満たすかを `@github/copilot-sdk` 1.0.13 の `dist/generated/rpc.d.ts` で確認した。**衝突しない。**

| 確認したもの | 実測 |
|---|---|
| `CopilotUserResponse.quota_snapshots` | **宣言あり** (`CopilotUserResponseQuotaSnapshots` 型) |
| `CopilotUserResponse.quota_reset_date` / `quota_reset_date_utc` | **宣言あり**。前者に「次にリセットされる日」という趣旨のドキュメントコメント付き |
| `CopilotUserResponseQuotaSnapshots` の枠 | `chat` / `completions` / `premium_interactions` の **3 つが名前で宣言されている** |
| `CopilotUserResponseQuotaSnapshotsChat` のフィールド | `entitlement` / `overage_count` / `overage_permitted` / `percent_remaining` / `quota_id` / `quota_remaining` / `remaining` / `unlimited` / `timestamp_utc` / `has_quota` / `quota_reset_at` / `token_based_billing` の **12 個すべて宣言あり** |
| `credits_used` | **宣言に無い。** `copilot_internal/user` (REST) には存在するが `getCurrentAuth` は返さない → **SDK が型に無いフィールドを落としている。`credits_used` に依存しない** |
| `copilotUser` を持つ `AuthInfo` バリアント | `AuthInfo` は 8 つの union だが、**8 つすべてに `copilotUser?` が宣言されている**。union の分岐で取りこぼす罠は無い |

**つまり我々が使う値はすべて型に載っている。**`getQuota` 側が型に無い `hasQuota` / `tokenBasedBilling` を返すのとは逆で、**ADR-0009 の原則は `getCurrentAuth` の方が満たしやすい。**

ただし**全フィールドが optional (`?`)** なので、防御的パース (NFR-23) は依然として必須。消えた場合の壊れ方が `getQuota` より良いことが、この判断の核心である:

- **フィールドが消えた場合の壊れ方が違う。** `getCurrentAuth` 側が消えれば、防御的パースが**その枠を `unavailable` に落とし、FR-C-83 の理由つきで UI に出る** — 設計された、目に見える劣化である
- 一方 `getQuota` の `resetDate` は**消えずに間違った値を返し続ける**。**silent-wrong は silent-missing より高くつく**
- → **「間違った値を確実に取る」より「正しい値を取れないことがある」を選ぶ** (NFR-40 / INV-7)

**INV-2 との関係 (重要)**:

API 名に `Auth` が入るが、**認証情報は読まない**。読んでよいのは以下 5 つとその配下だけとし、**DTO にもこれ以外を定義しない** (INV-2 / FR-C-72 / NFR-31)。

`copilotUser.quota_snapshots` / `copilotUser.quota_reset_date` / `copilotUser.quota_reset_date_utc` / `copilotUser.copilot_plan` / `copilotUser.access_type_sku`

**読まない・DTO に定義しない**: `authInfo.type` / `authInfo.host` / `authInfo.login` / `copilotUser.login` / `copilotUser.analytics_tracking_id` (32 文字の識別子) / `copilotUser.endpoints` / `copilotUser.organization_*` / トークンに相当しうる一切のフィールド。実測した戻り値の形にトークン相当のフィールドは無かったが、**「無かったから読んでよい」ではなく「要る 5 つだけ読む」**を規約にする。

**却下した案**:

- **`account.getQuota` を使い続ける (FR-C-130 の文字どおり)** — 上記 1〜2。分母とリセット日が取れず、誤名フィールドを抱える
- **`getQuota` と `getCurrentAuth` を併用し、足りない分だけ後者で補う** — 2 ソースから同じ枠を組み立てることになり、**ADR-0003 の理由 3 / FR-C-25 と同じ「処理順で値が変わる」不安定さ**を持ち込む。しかも `getCurrentAuth` は `getQuota` の**上位集合**なので、補う必要が無い
- **REST `copilot_internal/user` を使う** — **公開 API ではない** (`docs.github.com/rest` に記載が無く、パスも `copilot_internal/`)。`getCurrentAuth` との差は **`credits_used` 1 フィールドだけ**で、その `credits_used` (chat で `1`) は他の 2 つの消費量 (1.6 / 2) と一致せず定義が分からない。**互換性の約束が無いものを、得るもの 1 フィールドのために主経路に入れない**。加えて外向き通信を 1 本増やすことになる (INV-3 の例外は利用枠取得のみ = 経路が増えても不変条件違反ではないが、増やす理由が無い)
- **`session.usage.getMetrics` などセッション側 API で代用する** — 枠 (アカウント単位) とセッション消費は別物。FR-C-132 の用途はローカルの `events.jsonl` で足りる (ADR-0013)

**帰結**:

- T-6.3 の対象 API を `account.getQuota` から `account.getCurrentAuth` に差し替える。**要求本文 (FR-C-130) は書き換えず、差異を OQ-06 に記録した**
- **2 秒ポーリングに載せない** (FR-C-135 / INV-4)。SDK 呼び出しはネットワークと外部ランタイムを伴う
- Rust からこの API をどう呼ぶか (FR-C-137 の言語バインディング) は**未解決のまま**。測定は Node の TypeScript バインディングで行った (OQ-08)。**呼べないと分かったら、その時点で枠は `unavailable` になる** — 推定値で埋めない

## ADR-0018 — 経路 B (GitHub REST 課金 API) は「履歴」専用に降格し、v1 では実装しない

**状態**: 採用 (2026-09-08、T-0.8 の実測を受けて新規)

**文脈**: OQ-12 は当初「**月次 AI Credits の分母は経路 B にしか無い**」という前提で立てられ、段階 6 のブロッカーとして扱われていた。T-0.8 の実測で**前提が崩れた**。

- **分母 (`entitlement`) とリセット日 (`quota_reset_date`) は経路 A で取れる** (ADR-0017)
- **公開課金エンドポイントは 10/10 が 404。** うち 5 件は `documentation_url` に具体的なアンカーが返り、`gh` も `This API operation needs the "user" scope` を出す → **404 の真因はスコープ不足で、エンドポイント自体は実在する**
- 残り 5 件は汎用トップ (`https://docs.github.com/rest`) しか返らず、**パス名自体が実在しない可能性がある** (プローブ作成時に推測で並べたものを含む)
- **組織 / Enterprise は試行対象が 0 件** (`user/orgs` が 0)。FR-C-140 の経路は 1 度も叩けていない

**判断**: **v1 では経路 B を実装しない。** 経路 B が担うのは「**アカウント全体の月次消費額の履歴**」(FR-C-138 / 139) と「**組織 / Enterprise 管理下の枠**」(FR-C-140) だけとし、いずれも `unavailable` として出す。

**理由**:

1. **ゲージが経路 B なしで成立する。** 分母・残量・率・リセット日・適用有無はすべて経路 A で揃う。**ブロッカーではなくなった**
2. **測っていない挙動に実装を賭けない。** グループ 1 の 5 件が `user` スコープで 200 を返すかは**未測定**。無料プラン / 個人アカウントでは 404 のままという可能性が残る。**`gh auth refresh -s user` は実行していない** — ユーザーの資格情報 (スコープ) を、調査のために勝手に広げない
3. **組織 / Enterprise は検証手段が無い。** 手元のアカウントに組織が 0 件。**実測できない経路をコードで分岐だけ用意すると、動かないコードが残る**
4. **失敗経路の実装コストが実装しない場合より高い。** FR-C-142 の下限間隔と指数バックオフ、FR-C-140 の 403 / 404 の切り分けをすべて書いたうえで、返るのが 404 だけと分かっている

**却下した案**:

- **`copilot_internal/user` を経路 B の実体として使う** — 非公開 API。ADR-0017 の却下案を参照。**200 が返るからといって、経路 B の要求 (履歴・組織) を満たすわけでもない** (このエンドポイントは現在値のスナップショットしか返さない)
- **`gh auth refresh -s user` してから再測定し、その結果で実装する** — **ユーザーの資格情報のスコープを恒久的に広げる操作**であり、調査のために実行しない。ユーザーが自分で広げると決めたときに再測定する
- **経路 B を「未実装」ではなく「実装したが常に失敗する」形にする** — 動かないコードとテストを抱えるだけ。**取得不可は取得不可として表現する** (NFR-43) 方が安く、UI にも正しく出る

**帰結**:

- **T-6.5 (経路 B) は優先度を下げ、`保留 (OQ-12 待ち)` にする。** 再開条件は「(a) `user` スコープを持つアカウント、または (b) 組織 / Enterprise 管理下のアカウントで実測できたとき」
- FR-C-83 の「何をすれば取れるようになるか」に、**`user` スコープが要る旨を出す**。取れないことを黙って隠さない
- **FR-C-140 (個人 / 組織で叩くエンドポイントが違う) は未検証のまま残る。** 要求本文は書き換えず、OQ-12 に記録した

## ADR-0021 — `workspace.yaml` と ISO8601 は自前の最小パーサで読む

**状態**: 採用

**日付**: 2026-09-11

**文脈**: NFR-10 (依存を増やす前に ADR)。`workspace.yaml` は実測 375 バイトのフラットなスカラー 9 キーのみ、ISO8601 は `...Z` 固定書式のみ観測。タイムスタンプパースは段階 2 の利用状況紐付け (T-2.1〜2.7) で初出現。

**判断**: `workspace.yaml` は列 0 の `key: value` だけを拾う自前パーサ (`src-tauri/src/copilot/parser.rs::parse_workspace_yaml`)、ISO8601 は固定書式のみ対応する自前パーサ (`src-tauri/src/util/time.rs::parse_iso8601_ms`) を実装。

**理由**:

- **`serde_yaml`** — メンテナンス終了済み。不要な攻撃面。実測では複雑な YAML 機能を 1 つも使わない (ブロックスカラー / アンカー / エイリアス / マルチラインキーなし)
- **`chrono` / `time` crate** — バイナリサイズ・ビルド時間に対して、1 書式のみの対応では割に合わない。常駐アプリの軽さ (NFR-10)
- **自前パーサの実装コスト** — `workspace.yaml` は行走査 + 正規表現 1 つ (実装 20 行程度)。ISO8601 は固定書式なので substring / split で対応 (実装 15 行程度)。テストは別 (5 ケース / 4 ケース)

**サポート範囲**:

- `workspace.yaml`: キー = `id` / `cwd` / `client_name` / `name` / `created_at` / `updated_at` のみ
- ISO8601: RFC3339 の `YYYY-MM-DDTHH:MM:SS.sssZ` と `YYYY-MM-DDTHH:MM:SS.sss±HH:MM` (オフセット付き) のみ

**拡張の条件** (手書きパーサの限界):

- 実データで ブロックスカラー / 複雑な構造 / 別の ISO8601 書式が観測されたら、その時点で ライブラリ導入を再検討

**却下した案**:
