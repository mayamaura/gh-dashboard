1. 目的

1.1 解決する課題

A. コーディングエージェントの稼働が見えない

複数の VS Code ウィンドウとターミナルで Copilot を並行運用すると、次が把握できなくなる。

  1. 利用枠 (AI Credits / クォータ) の消費状況がすぐに見えない
  2. どのセッションが今動いていて、どれが止まっているか分からない
  3. どのエージェントがどのサブエージェント・委任タスクに指示を出しているかが見えない
  4. 「どうエージェントが動いたか」を後から振り返る手段がない

B. 開発中プロジェクトの所在と状態が見えない

  1. 動かすたびに「フォルダを思い出す → エクスプローラーを開く → ターミナルを開く → npm run dev → 採番されたポートを確認」を繰り返している
  2. どれを最後にいつ触ったか、どれが放置されているかを一覧で把握できていない

1.2 想定利用者

開発者本人 1 名 (個人利用)。配布・マルチユーザー対応・組織展開は目的としない。

2.2 非対象

#やらないこと理由
N-1Copilot セッションの再開・強制終了・エージェントへの介入「見る・振り返る」に集中する。誤操作の代償が読み取り専用機能とは桁違い
N-2プロジェクトの作成・削除・移動同上
N-3ビルド / テスト / デプロイの実行dev サーバー起動以外のプロセス管理を持ち込まない

N-5Copilot の既存設定ファイル (settings.json / config.json) の書き換え一切行わない。Copilot 側のデータはすべて読み取り専用。ファイルを置く必要が生じても、既存ファイルの編集ではなく新規ファイルの追加に限る
N-6認証情報の読み取り認証情報・OAuth トークン・MCP シークレットは読まない。DTO にフィールドを持たせることすらしない
N-7セッション内容・プロジェクト情報の外部送信利用枠の取得のために GitHub の API を叩くことは許容するが、こちらから内容を送らない
N-8GitHub 側の課金設定 (予算 / 支出上限) の変更表示のみ
N-9LLM による要約・日記生成本仕様のスコープ外
N-10複数プロセス構成 (frontend + backend) の専用管理 UI起動コマンド上書き欄に複合コマンドを書く運用でカバーする

5. 機能要求: プロジェクト機能 (FR-P)

5.1 スキャンと一覧化

ID優先度要求根拠
FR-P-01必須スキャン対象フォルダ直下の 1 階層のみを走査し、ディレクトリのみを候補とする。再帰しない深い再帰は node_modules / .venv / target の除外リスト管理を招き、走査時間も読めなくなる。ファイルを候補から外せば *.zip 等は自然に落ちる
FR-P-02必須スキャン対象フォルダはユーザーが追加/削除できる。未登録のときは既定フォルダ (%USERPROFILE%DocumentsProjects) をその場限りの対象として使うだけで、DB には書き込まない既定フォルダを自動登録すると「削除しても次回スキャンで復活する」削除不能状態になる
FR-P-03必須読み取れないフォルダ (存在しない / 権限なし) は警告ログを出してスキップし、スキャン全体を失敗させない
FR-P-04必須スキャン結果・git 状態・Copilot 利用状況を永続化しない。導出データとして要求時に読み直す。永続化するのは「スキャン対象フォルダ」と「手動調整」の 2 つだけディスクの現状を写しただけのデータを DB に持つと「実体は消えたのに DB に残る」「リネームで別プロジェクト扱いになる」同期ずれの世話が恒久的に発生する
FR-P-05推奨スキャン結果はプロセス内メモリにキャッシュし、再スキャンを伴わない操作 (手動調整の保存など) では再利用する
FR-P-06必須ディスク走査は UI スレッドを塞がない実行経路で行うUI スレッドでの同期 IO はアプリ全体を「応答なし」にする

5.4 手動調整 (override)

ID優先度要求
FR-P-30必須次の項目をプロジェクトごとに手動調整でき、path_key をキーに永続化する: 表示名 / 起動コマンド上書き / 作業ディレクトリ上書き / 並び順 / 非表示 / アーカイブ
FR-P-31必須手動調整は再スキャンしても失われない (path_key でマージする)
FR-P-32必須作業ディレクトリ上書きは絶対パスでもルートからの相対パスでも受け付け、保存時に実在するディレクトリかを検証し、存在しなければ拒否して DB に書き込まない
FR-P-33推奨自動判定は「候補の提示」、上書きは「最終決定」という役割分担にする。自動判定ロジックを個別事情に合わせて歪めない
なぜこの要求があるか

FR-P-32 が要る理由: リポジトリルートを作業ディレクトリにして、起動コマンドにルートからの相対パス (.\backend\.venv\Scripts\python.exe -m ...) を書きたい構成が実在する。自動判定が frontend/ を選ぶと相対パスが解決できず起動が失敗するため、上書きが必要になる。

5.6 Copilot 利用状況の紐付け

ID優先度要求
FR-P-50必須プロジェクトごとに Copilot の利用状況を読み取り専用で表示する: 保持セッション数 / 最終利用日時 / 直近セッションのタイトル / 稼働中か / 直近セッションのクレジット消費・追加行数・削除行数
FR-P-51必須セッション履歴とプロジェクトの対応付けは履歴側に記録された作業ディレクトリ (cwd) を正規化した path_key の完全一致を最優先とする
FR-P-52必須フォルダ名フォールバックを持つ。完全一致が無く、かつ ①その cwd がディスク上に存在せず、②同じフォルダ名を持つスキャン済みプロジェクトがちょうど 1 件で、③そのプロジェクトにまだ完全一致の履歴が紐付いていない — の 3 条件すべてが成立するときに限り紐付ける
FR-P-53必須フォールバックで紐付けた場合はその旨を UI に明示する (「旧パスの履歴 (フォルダ名で照合)」等)。推測による紐付けを事実として提示しない
FR-P-54必須同一 path_key に複数の履歴候補が競合したらセッション数が多い方を採用する。完全一致とフォールバックが競合したらフォールバック側を捨てる (合算しない)
FR-P-55必須巨大なログの全文パースを行わない。最終利用日時とタイトルは末尾数 KB、作業ディレクトリは先頭数十 KB の部分読みで求める
FR-P-56必須ファイルの mtime を判定に使わない。中身のタイムスタンプを読む
FR-P-57必須「稼働中」の判定は状態ファイルの存在だけでなく、PID の生存確認を併用する
FR-P-58必須履歴が一切ないプロジェクトは「触ったことがない」として利用状況を持たせない (空欄で埋めない)
なぜこの要求があるか

FR-P-52 が要る理由: エージェントは作業ディレクトリのパスをキーに履歴を保存するため、プロジェクトフォルダを移動・リネームすると履歴との紐付けが切れる。とくに VS Code の Copilot Chat はワークスペースフォルダの URI から導いたハッシュでセッションを保存するため、フォルダが動くと過去セッションが丸ごと孤児化する (付録 A.2)。完全一致だけに頼ると、フォルダを一度整理しただけで機能が実質使えなくなる。

FR-P-55 / 56 が要る理由: セッションログには数 MB のファイルが実在するため全文パースは成立しない。また PC 移行やバックアップ復元により複数ファイルが同一 mtime になることがあり、mtime を信頼した判定は壊れる。

FR-C-22必須サブエージェント実行の主キーは、親側と子側の両方に必ず存在する識別子とする。片側にしか存在しない ID を主キーにしない
FR-C-23必須親側でサブエージェント起動を見つけた時点で行を作成し、以降同じキーでマージする
FR-C-24必須バックグラウンド起動の「起動しただけ」の暫定応答を完了として扱わない。本当の完了通知が届くまで実行中のままにする
FR-C-25必須完了通知は単一のソースからのみ拾う。同じ通知が複数のレコード種別に重複して現れる場合、複数ソースから拾うと終了時刻が「どのソースを最後に処理したか」に依存する不安定な値になる
FR-C-26必須完了通知の適用には2 段階の確認ゲートを通す (「同一バッチ内に起動レコードがある」または「既に該当行が存在する」もののみ適用)
FR-C-27必須「拒否 (親が呼び出しを拒否した)」と「失敗 / 中断 (実際に起動して終わった)」を混同しない
FR-C-28必須利用枠到達・レート制限・セッションのクレジット上限到達をイベントとして抽出し保持する: セッション / 発生時刻 / 種別 / リセット表示文言 / 生メッセージ
FR-C-29推奨サブエージェント側のメタ情報 (種別・説明・親の呼び出し ID・深さ・モデル) は差分の有無に関わらず毎回読み直してマージする
なぜこの要求があるか

FR-C-22 が要る理由: 親側の呼び出しレコードと子側のログで異なる ID が振られている場合、片側にしか無い ID を主キーにすると (a) 拒否されたケースでキーを捻出できず、(b) 親の行と子のファイルが別々のインデックス実行に分かれたとき親子関係を復元できなくなり、系統図がフラットに退行する。

FR-C-24〜26 が要る理由: バックグラウンド実行のエージェントは起動 1〜2 秒後に「起動した」という暫定応答を書き、本当の完了は数分後に別のレコードとして届くことがある。暫定応答を完了とみなすと、数分動いた実行が「1 秒」と記録される。逆に完了通知を無条件に適用すると、エージェント以外のバックグラウンド実行 (シェルコマンド等) で幽霊行ができる。

仕様への影響:

  3. 超過を 100% でクランプしない (FR-C-90)。上限打ち止め設定でない限り、消費は付与額を超えて伸びる。
  4. 課金体系は実際に一度変わっている。 単価・付与額・枠の名前をコードに埋め込まず、実行時に読む (FR-C-134)。
