ADR-0001 — デスクトップシェルに Tauri v2 を使う

状態: 採用

文脈: 常駐アプリとして軽量であることが要求されている (NFR-10)。ランタイム同梱や常駐サービス追加は設計判断の文書化を求められる。一方で、Windows の Job Object を叩く、数百 MB のログを差分パースする、といったネイティブ寄りの処理が要求の中心にある (FR-P-61 / FR-C-01)。

判断: Tauri v2 (WebView2) + Rust コアを採用する。

理由:

  • Windows 11 は WebView2 を標準搭載しているため、ランタイムを同梱せずに済む。Electron は Chromium を丸ごと抱えるので NFR-10 に反する
  • 差分パース・プロセスツリー管理・Job Object という要求の中心が、そのまま Rust の得意分野に重なる
  • 要求 5.2 の種別判定リストで Tauri が 1 位に置かれている = 想定利用者が Tauri プロジェクトを日常的に扱う

代償: WebView2 のバージョン差でレンダリングが変わりうる。Rust のビルド時間が長い。

却下した案: Electron (NFR-10 に反する) / WPF・WinUI (図表の自前描画とレイアウト調整のコストが高い) / Web アプリ + ローカルサーバー (常駐の軽さとプロセスツリー管理に不利)

ADR-0002 — 永続化は SQLite 1 本。導出データは持たない

状態: 採用

文脈: DR-01〜03。「何でも保存する」誘惑への予防線が要求として明示されている。

判断: %LOCALAPPDATA%\gh-dashboard\app.db の SQLite 1 本。置くのは「スキャン対象フォルダ」「手動調整」「セッションログの索引・集計」だけ。

理由: ディスクの現状を写しただけのデータを DB に持つと、「実体は消えたのに DB に残る」「リネームで別プロジェクト扱いになる」という同期ずれの世話が恒久的に発生する。一方で数百ファイルを毎回全走査してはセッション一覧すら描けないため、索引だけは例外として持つ。

帰結: プロジェクトスキャン結果・git 状態・Copilot 利用状況・dev サーバーのログは、すべてプロセス内メモリのみ。詳細は データモデル。

ADR-0003 — セッション本文を複製せず、バイトオフセットで索引する

状態: 採用 (2026-09-08、OQ-02 の実測で前提が成立。あわせて「自前索引を続けるか」を再判断した)

文脈: FR-C-02。セッションログは数百 MB。実際に読み返されるのは「ビューアで開いた 1 レコード」だけ。

判断: 索引には ファイルパス + バイトオフセット + バイト長 + メタデータ + 140 字プレビュー のみを保存し、本文は開いた瞬間にシーク読みする。events.jsonl を索引・集計・本文の唯一の正とする。

前提は実測で成立した (OQ-02)

「生改行を含む行 22 件」はプローブの別項目で、JSON としてはエスケープ済みの文字列値のこと。行分割は壊れていない (parse 失敗 0 件が根拠)。

なぜ session-store.db に乗り換えないのか

OQ-05 で <COPILOT_HOME>/session-store.db が 書き込み中でも読み取り専用で開けた (12/12 成功、2〜4ms)。assistant_usage_events はモデル別トークン・total_nano_aiu・agent_id・parent_tool_call_id を持ち、FR-C-20 の集計をほぼ肩代わりできる。それでも索引の正を移さない。

  1. 本文レコードが DB に無い。 3 セッションで turns は 2 行、events.jsonl は 77 レコード。checkpoints / session_files / session_refs / forge_trajectory_events は 0 行。加えて turns にはバイトオフセットに相当する位置情報が無く、FR-C-120 の「1 レコードだけシーク読み」が成立しない
  2. 読み取り専用オープンの安全性を、測っていない条件まで広げられない。 12/12 の成功はすべて CLI が実行中 (= -shm を他プロセスが保持している) 状態での測定。writer 不在で -wal が残った DB を開くと、SQLite は復旧のために -wal / -shm へ書きに行くことがある。それは INV-1 (Copilot 側に書かない) の違反になる。不変条件を未測定の条件に賭けない
  3. 集計ソースを 2 つ持つと、FR-C-25 と同じ不安定さをセッション集計に持ち込む。 どちらを最後に処理したかで値が変わる。events.jsonl だけで session.shutdown.data の totalNanoAiu / modelMetrics / agentMetrics / tokenDetails が揃い、totalNanoAiu / 10^9 = AI Credits は 2 セッションで CLI フッター表示と一致した (0.38 / 0.6)
  4. 壊れ方の粒度が違う。 events.jsonl は防御的パース (FR-C-13) で「その 1 行だけ落とす」に劣化させられる。DB はスキーマが変わるとクエリごと落ちる (schema_version テーブルが存在すること自体、変更が前提であることを示す)

却下した案:

  • session-store.db を索引の正にする — 上記 1〜4
  • 併用し、本文は events.jsonl・集計は DB から取る — 上記 3。2 ソースの突き合わせコストに対して得るものが「既にログから取れる数字」しかない
  • レコード境界を別テーブルに記録する — OQ-02 が成立したので不要。オフセットで足りる
  • session-store.db を起動時にコピーして読む (DR-05 の案) — 本体 4,096 バイトに対し WAL が 609,792 バイト。本体だけコピーしても中身が無い

帰結: session-store.db の扱いは ADR-0013 に分離した。セッションのメタ情報 (cwd / エントリポイント / タイトル候補) は、DB ではなく session-state/<id>/workspace.yaml (375 バイト) から取る。workspace.yaml の name は初回プロンプトの本文がそのまま入るため、140 字プレビューの上限を掛けて扱う (INV-6)。

ADR-0004 — ライブ監視のタイマーは UI 側に置く

状態: 採用

文脈: FR-C-41。「タブを離れたら確実に止まる」ことが要求。

判断: 2 秒タイマーは React コンポーネントの useEffect に置き、バックエンドには常駐ポーリングループを作らない。

理由: コンポーネントのマウント / アンマウントが「タブを見ているか」と厳密に一致する。バックエンドに置くと開始 / 停止の往復と状態管理が増え、「離れたら確実に止まる」保証がコードから読み取れなくなる。

帰結: 最小化の検知だけはネイティブ側から window-visibility イベントで送る必要がある (IR-46)。WebView の visibilitychange は最小化で発火しないため。

ADR-0005 — 図表は自前 SVG 描画。チャートライブラリを入れない

状態: 採用

文脈: FR-C-163 / NFR-13。ゲージ・ガント・系統図が必要。

判断: すべて自前の SVG + CSS で描く。アニメーションは GPU 合成されるプロパティ (transform / opacity / stroke-dashoffset / filter) に限定する。

理由: 必要な図は 3 種類だけで、いずれも汎用チャートライブラリの機能をほとんど使わない。常駐アプリのバンドルサイズとメモリに対して割に合わない。系統図とガントは同じ木構築結果を共有する必要があり (FR-C-114)、汎用ライブラリのデータモデルに合わせる方がむしろ制約になる。

帰結: アニメーション設定 (自動 / 入 / 切) を自前で持ち、自動 は prefers-reduced-motion に追随する (FR-C-162)。

ADR-0006 — DTO の型は生成せず、手で同期する

状態: 採用 (再検討の余地あり)

文脈: Rust の DTO と TypeScript の型を一致させる必要がある。ts-rs / specta のような生成器がある。

判断: v1 では生成器を入れず、src/types/dto.ts を手で書いて同期する。ただし呼び出しは src/ipc/commands.ts の型付きラッパーに集約する (IR-31)。

理由: 生成器はビルド手順と依存を増やす (NFR-10)。DTO の数は数十で、境界は 1 ファイルに集約されているため、手動でも破綻しにくい。

注意

この判断は IR-30 の事故 (path_key → pathKey) を防げない。引数名のケース変換は型の一致とは別の問題で、生成器を入れても防げない。防ぐのは rename_all = "snake_case" の全コマンド適用と、ラッパー経由の呼び出しの 2 つ。

DTO が 50 個を超えたら生成器の導入を再検討する。

ADR-0007 — 状態管理ライブラリを入れず、小さな共有ストアを自前で持つ

状態: 採用

文脈: FR-C-161 / 164。長時間処理の進行状態とタブ別スナップショットは、タブ切替で破棄されてはいけない。

判断: useSyncExternalStore を使った 100 行程度の自前ストア (src/store/appStore.ts) を持つ。Redux / Zustand / Jotai を入れない。

理由: 共有したい状態は「インデックス進捗」「最終取得時刻」「タブ別スナップショット」「アニメーション設定」程度で、非同期の複雑な合成を必要としない。React 標準の useSyncExternalStore で足りる (NFR-13)。

ADR-0008 — ドキュメントは Markdown 原本 + HTML 生成

状態: 置換 (2026-09-12、ADR-0022 に置換)

文脈: ドキュメント一式を HTML で提供する必要がある。一方で、手書きの HTML を十数枚維持するのは差分レビューにも AI エージェントの編集にも向かない、と当時は判断した。

判断: docs/source/*.md を原本とし、tools/md2doc.mjs で docs/*.html を生成する。生成物もコミットする (ビルドなしでブラウザから読めるようにするため)。

運用:

  • 編集するのは docs/source/*.md だけ。docs/*.html を直接編集しない (次回生成で消える)
  • npm run docs:build で再生成、npm run docs:check で生成物が原本と一致するか検査
  • docs/index.html だけは手書き (カード配置のため)。ナビゲーションは docs/assets/docs.js の NAV に一本化

代償: 変換器が対応する記法の範囲でしか書けない。凝った記法が必要になったら、記法を増やすのではなく書き方を変える。

置換の理由: 原本と生成物の二層構成は、AI エージェントに「どちらを読み・どちらを編集するか」を毎回判断させるコストを生んだ。詳細は ADR-0022。

ADR-0009 — 利用枠は「取れないこと」を一級の状態として扱う

状態: 採用 (2026-09-08、OQ-06 の実測で補強。同日 T-0.8 で実測 2 点を訂正)

文脈: FR-C-80〜95 / 130〜144。取得経路は A (SDK) → B (REST) → C (推定) と降格しうる。OQ-06 の実測次第では A が使えず B が主役になる。

判断: QuotaSource を actual / estimated / unavailable の 3 状態を持つ型として定義し、枠ごとに独立して持つ。unavailable には「何をすれば取れるようになるか」を必ず添える。

理由: 取れない値を 0 で埋めた瞬間、そのゲージは嘘になる (NFR-40)。「取得不可」はエラーではなく正常な状態のひとつ。

実測による補強 (OQ-06)

この判断は「念のため」ではなく、実測で必要になった。

  • 経路 A が返す枠は chat / completions / premium_interactions の 3 つだけ。ai_credit という名前の枠は無い。 ただし T-0.8 で訂正: 3 枠には entitlement (付与額 200 / 2000 / 0) と quota_reset_date (2026-10-01) が付いており、ゲージの分母とリセット日は経路 A で取れる (account.getCurrentAuth)。unavailable から始まるのは「アカウント全体の月次消費額を額で出す」用途だけになった
  • premium_interactions は entitlement = 0 かつ has_quota: false かつ percent_remaining: 0。 FR-C-131 は -1 (無制限) を名指ししているが、実在したのは 0 の方であり -1 は 1 度も観測していない。適用外の判定は has_quota === false を第一基準にし、entitlement <= 0 は 0 除算ガードとして併用する。percent_remaining: 0 をそのままゲージに載せない — FR-C-88 の 90% 以上 = 危険 に該当して、適用外の枠が真っ赤になる
  • 型宣言 (AccountQuotaSnapshot) に無い hasQuota / tokenBasedBilling が実際には返る。 型定義とランタイムに差がある。型に無いフィールドは次のバージョンで黙って消えうるので、消えたら該当の枠だけ unavailable に落ちる防御的パースを前提にする (NFR-23 / NFR-43)。どの API を使うかの判断は ADR-0017
  • [訂正] resetDate は「問い合わせ時刻に追従する」のではない。 中身は利用枠スナップショットの観測時刻で、getCurrentAuth().authInfo.copilotUser.quota_snapshots.*.timestamp_utc とミリ秒まで同一だった (SDK と REST を数秒差で別プロセスから叩いて確認: 2026-09-08T11:58:34.381Z = 2026-09-08T04:58:34.381-07:00)。同一プロセスで 3 回続けて呼んでも値は動かない。リセット日として表示しない結論は変わらないが、理由が変わった。本物の月次リセット日は copilotUser.quota_reset_date (2026-10-01)
  • 観測時刻としては使えるが、鮮度 (FR-C-86) には足りない。 「値が変化したときだけ更新される」保証が無く、quota_remaining が 198.4 のまま timestamp_utc だけが 3 回動いた実例がある。「この値が動いた = 利用枠が変わった」とは言えない。→ observed_at は我々の側で「値が変わったときだけ」更新して持つ (結論は据え置き、根拠を差し替え)

帰結: UI は 3 状態すべてに描画を持つ。「実値がある枠」と「推定の枠」を同じ画面に並べてよいが、同じ枠の中で混ぜてはいけない (FR-C-84 / 144)。枠ごとの取得経路の割り当ては ADR-0015。

ADR-0010 — 単価・付与額・枠の名前をコードに埋め込まない

状態: 採用 (2026-09-08、OQ-06 の実測で帰結を更新。同日 T-0.8 で「$ 表示を検討する条件」を訂正)

文脈: 課金体系は 2026-06-01 に実際に変わっている (プレミアムリクエスト → AI Credits)。付録 A.4。

判断: モデル別の単価は models.list から実行時に読む (FR-C-134)。付与額・枠の名前も定数として持たない。

理由: プランとモデルの改定で必ず陳腐化する。埋め込んだ定数は、間違った金額を自信ありげに表示する形で壊れる。

実測: 単価が実行時にも取れなかった (OQ-06)

  • models.list({}) は呼べたが、返ったのは "auto" 1 件のみで billing フィールドが無い。 FR-C-134 が前提にしている経路が、この呼び方では成立しない
  • 1 AI Credit = $0.01 の裏取り材料も得られなかった。 getQuota の戻り値に金額単位のフィールドは 1 つも無い
  • 一方、totalNanoAiu / 10^9 = AI Credits は実測で一致した (382,635,000 → 0.38 / 598,806,000 → 0.6。いずれも CLI フッター表示と一致)

判断の追記 (帰結): 単価が実行時に取れないなら、金額 ($) 換算を出さない。

  • 消費は AI Credits 単位で表示する (例: 0.38 credits)。$ に換算しない
  • FR-C-89 は「額も併記する」(例 $6.20 / $10.00) と書いているが、その前提 (単価が取れる) が実測で成立していない。要求本文は書き換えず、OQ-06 / OQ-12 に「要求の前提が実測と異なる」として記録した
  • 単価が取れないことを「取れない」と表示する。代わりに二次情報の $0.01 を掛けない (INV-7 / NFR-40)

[訂正] 「分母が経路 B で取れたら $ 表示を検討する」の前提が変わった (T-0.8)

訂正前は「付与額 (分母) が経路 B で取れたら、その時点で $ 表示を検討する」と書いていた。前提が崩れた。

  • 分母は経路 B ではなく経路 A で取れる。 account.getCurrentAuth が entitlement (chat 200 / completions 2000 / premium_interactions 0) と quota_reset_date (2026-10-01) を返す (OQ-06 / ADR-0017)
  • それでも $ 表示は出せない。 残る欠落は「1 AI Credit が何ドルか」の 1 点。models.list は "auto" 1 件で billing を持たず、getCurrentAuth にも金額単位のフィールドは 1 つも無い
  • entitlement の単位すら確定していない。 chat の消費区間 (1.55, 1.65] にローカル実測 1.5525 credits が収まり、token_based_billing: true とも整合するので AI Credits 建ての可能性は高いが、1 アカウント・無料プラン (free_limited_copilot) の導出が 2 点あるだけ。要求 付録 A.4 が言う「月額プラン料金と同額のクレジット」との対応は測れていない

書き換え後の条件: $ 表示の条件は「単価が実行時に取れること」の 1 つに絞られた。 分母が取れたことは条件を満たさない。分母が取れた今も、AI Credits 単位で表示し、$ に換算しない。

却下した案: 1 AI Credit = $0.01 を定数として持ち、注釈で逃げる — 注釈は読まれない。数字が出ている時点でユーザーはそれを信じる。取れない値は出さない方が常に安全 (NFR-43 / 44)。

却下した案 (T-0.8 で追加): entitlement を「$ 建ての付与額」とみなして額表示に使う — 単位の裏取りが 1 アカウント・無料プランの区間一致 2 点しかない。free_limited_copilot の entitlement: 200 を「$200」とも「200 credits」とも断定できない。推定を実測として表示することになる (INV-7 / NFR-40)。

帰結: 金額を出す日が来たら、概算である旨を必ず添える (NFR-45)。キャッシュトークンの扱いや端数処理まで一致する保証はない。請求額の正は GitHub の課金画面。

ADR-0012 — statusLine フックを使わない

状態: 採用 (2026-09-08、OQ-04 の実測で再確認。判断は変わらない)

文脈: Copilot の statusLine フックは cwd / session_id / model / cost / context_window を渡してくれる。

判断: 採用しない。フック全般を使わない。

理由: statusLine には利用枠が載らない。載っている情報はすべて SDK と差分インデックスで代替できる。採用すると「ユーザーの設定ファイル (~/.copilot/settings.json) を書き換える」「中継用の実行ファイルを同梱する」という対価だけが残る。

実測による再確認 (OQ-04)

@github/copilot-sdk の dist/generated/rpc.d.ts に定義されているフックイベントを実際に確認した: sessionStart / sessionEnd / postResult / prePRDescription / errorOccurred / agentStop / subagentStart / subagentStop / preCompact / permissionRequest / notification。

sessionStart / sessionEnd は FR-C-40 の稼働判定に、subagentStart / subagentStop は FR-C-24〜26 の完了ゲートに、それぞれ直接効きそうに見える。それでも採用しない。

ADR-0013 — session-store.db は集計に使わない。読むとしても補助・任意・最良努力

状態: 採用 (2026-09-08、OQ-05 の実測を受けて新規)

文脈: OQ-05 で、<COPILOT_HOME>/session-store.db が CLI の書き込み中でも読み取り専用で開けた (12/12 成功、2〜4ms、journal_mode = wal)。スキーマには assistant_usage_events があり、モデル別トークン・total_nano_aiu・agent_id・parent_tool_call_id・initiator (user / agent / sub-agent) を持つ。FR-C-20 の集計をほぼ肩代わりできる形をしている。

判断: v1 では session-store.db を読まない。 索引・集計・稼働判定のいずれの経路にも入れない。

理由:

  1. INV-1 を未測定の条件に賭けられない。 12/12 の成功はすべて CLI が実行中 (= -shm を他プロセスが保持している) 状態での測定。writer 不在で -wal が残った DB を読み取り専用で開くと、SQLite は復旧のために -wal / -shm へ書きに行くことがある。それは「Copilot 側に書き込まない」の違反であり、動いてしまった場合に気づけない種類の違反
  2. 必要な情報が、DB を開かずに取れる。 セッションと cwd の紐付け・エントリポイント・タイトル候補・更新時刻は、session-state/<id>/workspace.yaml (375 バイト、プレーンテキスト) に揃っている。workspace.yaml の mtime は sessions.updated_at と 10ms 以内で一致した (3/3)。SQLite を開く理由が消える
  3. 集計を 2 ソースから拾うと、FR-C-25 と同じ不安定さを持ち込む (ADR-0003 の理由 3)
  4. INV-4 との相性が悪い。 2 秒ポーリング経路で他プロセスが書き込み中の SQLite を毎周期開くのは、ネットワークでも外部プロセスでもないが、待たされうる I/O である。workspace.yaml の stat と events.jsonl の stat で済むなら、そちらが安い

却下した案:

  • session-store.db を索引の正にする — ADR-0003 の 1〜4
  • sessions.updated_at を稼働判定に使う — 動くことは確認した (再開でちゃんと進む。created 17:10:51 → updated 17:14:22)。だが workspace.yaml の mtime が 10ms 以内で同じ値を与えるうえ、sessions.updated_at は最後のイベントより 4〜14 秒早い。理由 1 の risk を払ってまで採る価値がない (ADR-0014)
  • 起動時にコピーして読む (DR-05 の案) — 本体 4,096 バイトに対し WAL が 609,792 バイト。本体だけコピーしても中身が無く、WAL ごとコピーすればサイズと整合性の両方を抱える
  • turns から本文を読む — 3 セッションで 2 行しか無く、events.jsonl の 77 レコードに対応しない。本文の正ではない
注意

INV-6 との関係を誤解しないこと。 turns には user_message / assistant_response の本文がそのまま入るが、これは Copilot 側の DB であって我々の app.db ではない。読むこと自体は INV-6 に触れない。INV-6 が禁じているのは我々の DB に本文を複製することである。 一方 workspace.yaml の name (初回プロンプトの文面がそのまま入る) を我々の DB に保存する場合は、140 字プレビューの上限が掛かる (FR-C-02 / INV-6)。

帰結:

  • 段階 4 は session-store.db に一切依存せずに完成させる。OQ-05 は「読めることは分かったが使わない」として 一部判明 のまま残す
  • 将来 events.jsonl の形式が壊れたときの代替経路の候補として名前だけ残す。採用するときは、まず「writer 不在時の読み取り専用オープンが書き込みを起こさないか」を実測する

  1. getQuota は必要な 2 つを落としている。 ゲージに要る小数の残量 (quota_remaining) と本物の月次リセット日 (quota_reset_date) が返らない。前者が無いと率と消費量の整合が取れず (usedRequests は整数丸め)、後者が無いと FR-C-85 の「リセット後の観測を除外」が実装できない
  2. getQuota は 1 つのフィールドを誤った名前で返す。 resetDate の中身はリセット日ではなくスナップショットの観測時刻である。SDK と REST を数秒差で別プロセスから叩き、resetDate = 2026-09-08T11:58:34.381Z と timestamp_utc = 2026-09-08T04:58:34.381-07:00 がミリ秒まで一致することで確認した。間違った名前のフィールドは、読んだ人が正しく使う方が難しい
  3. getQuota を使っても「型宣言だけに頼る」ことはできない。 hasQuota / tokenBasedBilling は型に無いのに返る。どちらの API を選んでも防御的パース (NFR-23) は必須であり、getQuota を選ぶ理由が「型に載っているから」にはならない

型宣言の確認 (ADR-0009 の原則との関係) — 2026-09-08 に実測で解決:

ADR-0009 は「宣言されたフィールドだけを使う」と書いた。getCurrentAuth 側がこれを満たすかを @github/copilot-sdk 1.0.13 の dist/generated/rpc.d.ts で確認した。衝突しない。

確認したもの実測
CopilotUserResponse.quota_snapshots宣言あり (CopilotUserResponseQuotaSnapshots 型)
CopilotUserResponse.quota_reset_date / quota_reset_date_utc宣言あり。前者に「次にリセットされる日」という趣旨のドキュメントコメント付き
CopilotUserResponseQuotaSnapshots の枠chat / completions / premium_interactions の 3 つが名前で宣言されている
CopilotUserResponseQuotaSnapshotsChat のフィールドentitlement / overage_count / overage_permitted / percent_remaining / quota_id / quota_remaining / remaining / unlimited / timestamp_utc / has_quota / quota_reset_at / token_based_billing の 12 個すべて宣言あり
credits_used宣言に無い。 copilot_internal/user (REST) には存在するが getCurrentAuth は返さない → SDK が型に無いフィールドを落としている。credits_used に依存しない
copilotUser を持つ AuthInfo バリアントAuthInfo は 8 つの union だが、8 つすべてに copilotUser? が宣言されている。union の分岐で取りこぼす罠は無い

つまり我々が使う値はすべて型に載っている。getQuota 側が型に無い hasQuota / tokenBasedBilling を返すのとは逆で、ADR-0009 の原則は getCurrentAuth の方が満たしやすい。

ただし全フィールドが optional (?) なので、防御的パース (NFR-23) は依然として必須。消えた場合の壊れ方が getQuota より良いことが、この判断の核心である:

  • フィールドが消えた場合の壊れ方が違う。 getCurrentAuth 側が消えれば、防御的パースがその枠を unavailable に落とし、FR-C-83 の理由つきで UI に出る — 設計された、目に見える劣化である
  • 一方 getQuota の resetDate は消えずに間違った値を返し続ける。silent-wrong は silent-missing より高くつく
  • → 「間違った値を確実に取る」より「正しい値を取れないことがある」を選ぶ (NFR-40 / INV-7)

INV-2 との関係 (重要):

却下した案:

  • account.getQuota を使い続ける (FR-C-130 の文字どおり) — 上記 1〜2。分母とリセット日が取れず、誤名フィールドを抱える
  • getQuota と getCurrentAuth を併用し、足りない分だけ後者で補う — 2 ソースから同じ枠を組み立てることになり、ADR-0003 の理由 3 / FR-C-25 と同じ「処理順で値が変わる」不安定さを持ち込む。しかも getCurrentAuth は getQuota の上位集合なので、補う必要が無い

  • session.usage.getMetrics などセッション側 API で代用する — 枠 (アカウント単位) とセッション消費は別物。FR-C-132 の用途はローカルの events.jsonl で足りる (ADR-0013)

帰結:

  • T-6.3 の対象 API を account.getQuota から account.getCurrentAuth に差し替える。要求本文 (FR-C-130) は書き換えず、差異を OQ-06 に記録した
  • 2 秒ポーリングに載せない (FR-C-135 / INV-4)。SDK 呼び出しはネットワークと外部ランタイムを伴う
  • Rust からこの API をどう呼ぶか (FR-C-137 の言語バインディング) は未解決のまま。測定は Node の TypeScript バインディングで行った (OQ-08)。呼べないと分かったら、その時点で枠は unavailable になる — 推定値で埋めない

ADR-0023 — 差分インデックスの集計は「累積せず数え直す」、オフセットは 1 箇所でだけ進める

状態: 採用 (2026-09-12、T-4.2〜4.8 / 4.11 の実装で決定)

文脈: 差分インデックスは「同じファイルを何度読み直しても結果が同じ」でなければならない。追記・truncate・クラッシュ・多重起動のどれが起きても、sessions / turn_index / subagent_runs が一意に定まる必要がある (FR-C-03〜07 / 14)。

判断:

  • 件数列 (turn_count / agent_count / quota_event_count) は加算しない。 バッチごとに COUNT(*) で数え直す (store::refresh_session_counts)。集合が正で、件数はその長さ (FR-C-51 と同じ理屈)
  • 集計はバッチごとに書く。 ファイル末尾でまとめて書くと、途中で落ちたときに「オフセットだけ進んで集計は空」という再実行しても直らない状態ができる (次回は保存済みオフセットから読むので session.shutdown を二度と見ない)
  • オフセットを進める場所は flush_batch の最後 1 箇所だけ。 レコード挿入・サブエージェントのマージ・集計・オフセット更新を同一トランザクションに入れ、オフセットを最後に置く (FR-C-04)
  • 差分実行の NULL で既存値を消さない。 sessions の upsert は COALESCE を通す。差分実行では「今回のバッチに session.shutdown が入っていない」ことが普通に起きる
  • 全再パース時は先に行を消す。 UNIQUE(file_path, byte_offset) は二重挿入を防ぐが、入れ替わったファイルの古い行を古いまま残す。Delta::Reparse ではその file_path の turn_index を削ってから 0 に戻す
  • 実行中フラグは Drop ガードで戻す (IndexingGuard)。end_indexing() を手で呼ぶ形だと、早期 return を 1 本足した瞬間にフラグが立ちっぱなしになり、再起動するまでインデックスが二度と動かなくなる
  • ストリーミング側の末尾断片判定も delta に置く (delta::committed_line)。split_committed はファイル全体を要求するため差分インデックス (FR-C-08) では使えないが、規則を 2 箇所に書かない。両者が同じ行に分解することをテストで固定した

却下した案:

  • 件数をバッチごとに加算する — 再パースや二重適用のたびにずれる。ずれたことに気付く手段が無く、直すには全削除して作り直すしかない。数え直しは idx_turn_session があるので実測でも安い (46 セッション / 1,041 レコードの初回が 344ms)
  • turn_index.nano_aiu にレコード単位のクレジット消費を入れる — そんな値はログに存在しない。totalNanoAiu は累計値なので、これを各レコードに入れると SUM した瞬間に多重計上になる。セッション単位の値だけを sessions.total_nano_aiu に持ち、turn_index.nano_aiu は 0 のままにする
  • subagent.completed.data.totalTokens を input_tokens / output_tokens のどちらかに入れる — 内訳が無い 1 つの合計値であり、どちらに入れても嘘になる (INV-7)。列が無いので保持しない
  • session.shutdown.data.agentMetrics からサブエージェントのトークンを補う — 実データ (46 セッション) の shutdown 50 件すべてに agentMetrics が無かった。隔離環境の 4/4 とは逆。片方の環境でしか観測できていない構造に依存しない。加えて ADR-0016 が完了判定のソースとして明示的に却下している
  • sessions.git_branch を索引時に埋める — 埋めるにはセッションの cwd ごとに git を起動することになり、インデックス 1 回で数十プロセスが立つ。プロジェクト一覧側が実時間で持っているので NULL のままにする
  • entrypoint 列に分類済みの値を保存する — 実データの client_name は 45/46 が sdk で、これがどの経路かを示す根拠が無い。生の値を列に残し、表示用の写像は読み出し時に行う (未知は Unknown)。分類を保存すると、後で写像を直しても再インデックスするまで直らない (NFR-40 / NFR-43)
注意

T-4.9 / T-4.10 は実装していない。 subagent_runs.status に書き込む値は 'running' だけで、'completed' / 'declined' へ遷移させる経路を持たない。subagent.completed が来ても ended_at を埋めない — 終了時刻を確定させることが FR-C-24〜26 のゲートそのものだから。根拠は ADR-0016 の注記と OQ-11 (2026-09-12 の実データでも拒否された委任・非同期委任とも 0 件)。

ADR-0024 — 稼働中サブエージェントは subagent.started ではなく agentId で拾う

状態: 採用

日付: 2026-09-12 (段階 5 / T-5.2・T-5.4 の実装時、実データの実測を受けて)

文脈: FR-C-50 / 51 は「稼働中サブエージェントの集合を作り、件数はその長さとする」と書く。素直な実装は「末尾ウィンドウ内に subagent.started があり、同じ toolCallId の subagent.completed が無いもの」である。これを実装して実データに掛けたら 0 件だった。

実測 (2bb4517d… / 293,339 バイト / 79 レコード)末尾からの位置64KB 窓に入るか
subagent.started252,883 バイト入らない
subagent.completed9,671 バイト入る
子が書いた最後のレコード (agentId つき)12,741 バイト入る

これは例外ではなく構造的な偏りである。 サブエージェントが長く走るほど、子が書くレコード (実測 38 件 / 240KB) が subagent.started を窓の外へ押し出す。つまり 「長く走っていて表示したいもの」ほど確実に取り逃す。 窓を 512KB に広げても先送りにしかならない (FR-C-08 / NFR-03 があるので全読みはできない)。

判断: 候補集合を次の和にする。除外は窓内の subagent.completed の toolCallId。

  1. 窓内に現れた agentId (トップレベルのフィールド)
  2. 窓内の subagent.started の data.toolCallId

根拠: agentId はサブエージェントに属するレコードだけに付き (OQ-01: 出現率 23.4%)、その値は子の toolCallId と一致する。実データのサブエージェント 2 件とも 1:1 で一致した (toolu_0179WxXYi4A1j6CuC1XX5RKA / call_DfZiFUaIGbm4q7AHWL1ejeVi)。走っているサブエージェントは今まさに書いているのだから、その agentId は必ず末尾付近にある — 窓の位置に依存しない。FR-C-22 (親側と子側の両方に存在する識別子を主キーにする) / ADR-0016 とも同じキーのままである。

評価順に依存がある: subagent.completed 自身も agentId を持つ。逆走査で完了 ID を先に集めてから agentId を評価しないと、完了したサブエージェントを自分の完了レコードで稼働中に復活させる。実装は match の後で agentId を評価する (テスト completed_subagent_is_not_revived_by_its_own_agent_id)。

実データでの確認 (隔離 COPILOT_HOME にコピーして検証。実データは読むだけ / INV-1):

  • subagent.completed あり → 集合は空 (誤検出なし)
  • subagent.completed を削って「走行中」を再現 → ["toolu_0179…"] / 活動状態 SubagentRunning。subagent.started だけの規則では 0 件だったケース

却下した案:

  • subagent.started だけを候補にする — 上記のとおり実データで取り逃す。しかも「0 件」は正常な表示と見分けがつかないので、壊れていることに気付けない
  • 常に 512KB 窓で読む — FR-C-47 に反するうえ、上の実測でも started は 252KB 先にある。1 回長く走ればすぐ超える。窓幅を増やす方向の解は原理的に効かない
  • サブエージェントのログファイルの mtime を見る (FR-C-50 の本文) — 実データではサブエージェントは親と同じ events.jsonl に書く。専用ファイルが無いので判定材料にならない (OQ-07)
  • DB (subagent_runs.status) を読む — FR-C-50 が明示的に却下している (更新ボタンを押すまで古い)。加えて T-4.9 / T-4.10 未実装で status は 'running' のまま (ADR-0023)

残る近似 (FR-C-52 と同種の既知の限界として受け入れる): サブエージェントが窓ぶんの期間まったく書かずに黙っている場合は取り逃す。ただしその間は親の events.jsonl も伸びないので、mtime 窓 (120 秒) でセッションごと非稼働に落ちる方が先に効く。

ADR-0025 — ライブ監視の末尾分類は 4 規則だけにし、許可待ち専用の規則を作らない

状態: 採用

日付: 2026-09-12 (段階 5 / T-5.2)

文脈: FR-C-45 ② の入力 (activity::TailRecord) を実レコードから作る関数が必要になった。既存の parser::scan_tail は物理的な最終行の timestamp を取るだけで、本文レコードを遡って探さない (FR-C-49 を満たさない)。実データ 46 セッションの物理的な最終行は 46/46 すべて session.shutdown だった。

判断: parser::classify_tail (純粋関数) を新設し、末尾ウィンドウの確定行を新しい行から古い行へ 1 回だけ辿る。規則は 4 つ。

  1. tool.execution_start があり、同じ toolCallId の tool.execution_complete がより新しい位置に無い → ToolUse
  2. assistant.turn_end → TurnEnded
  3. user.message → UserMessage
  4. どれにも当たらない / パースできない → Unrecognized (= 不明。空欄にも既定値にも倒さない / NFR-43)

assistant.message に規則を持たせない理由: ターン途中で止まっている場合、逆走査は同じターンの先頭にある user.message まで遡って規則 3 に当たり「生成中」になる。実データのレコード順 (user.message → assistant.turn_start → assistant.message) がそれを保証しているので、5 つ目の規則も TailRecord の 5 値目も要らない。

許可プロンプト待ちに専用規則を作らない理由 (FR-C-46): 実データのレコード順は tool.execution_start → permission.requested → permission.completed で、許可待ちの間は「complete の無い start」が最後に残る = 規則 1 に落ちる。加えて permission.requested は toolCallId を持たない (実測 82 件すべて permissionRequest / promptRequest / requestId のみ) ので、そもそも突き合わせキーが作れない。FR-C-46 の「両者は区別できない」がデータの形としても正しいことが確認できた。

却下した案:

  • scan_tail を拡張して兼用する — scan_tail は段階 2 (FR-P-56) の「最終活動時刻と shutdown 判定」用で、止まる位置が違う。1 つの関数に 2 つの停止条件を持たせると、どちらの呼び出し側も相手の都合で壊れる
  • permission.requested / permission.completed を突き合わせる — キーが無い。requestId は toolCallId と別物
  • 子 (サブエージェント) のレコードを分類から除外する — 除外してもしなくても結果が同じだった (どちらの経路でも ToolUse になる)。結果が変わらない分岐は書かない

ADR-0026 — ide/*.lock の PID 生存確認は win_job.rs に置き、headers を持つ構造体を定義しない

状態: 採用

日付: 2026-09-12 (段階 5 / T-5.13)

文脈: FR-C-70〜72。ADR-0014 が ide/*.lock を「IDE ワークスペース一覧専用」と位置づけた。FR-C-71 は PID が死んでいても行を残して「切断済み」にせよと言うので、PID の生存確認が要る。

判断:

  • is_process_alive(pid) を platform/win_job.rs に置く (INV-8: unsafe / FFI を書いてよい唯一のファイル)。OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION) + GetExitCodeProcess の 2 回のシステムコールのみ。プロセスを起動しないので INV-4 / FR-C-42 に触れない
  • lock の読み取り先構造体に headers フィールドを定義しない。 serde は未知フィールドを既定で捨てるので、宣言しないことがそのまま「読まない」になる

実データの lock の形 (2 件、値は伏せる): {socketPath, scheme, headers:{Authorization}, pid, ideName, workspaceFolders[], isTrusted}。headers.Authorization が実在する — INV-2 / FR-C-72 は仮定ではない。

却下した案:

  • #[serde(skip)] で headers を落とす — 「読んでから捨てる」形になり、値が一度メモリに載る。フィールドを書かなければ載らない
  • sysinfo クレートを足す — 2 回のシステムコールのために依存を 1 つ増やす理由がない (NFR-10)。windows-sys は Win32_System_Threading ごと既に入っている
  • tasklist / Get-Process を呼ぶ — 2 秒ポーリング経路での外部プロセス起動は INV-4 違反
  • WaitForSingleObject で判定する — 終了コード 259 の曖昧さは消えるが SYNCHRONIZE 権限が要る。IDE の接続表示にその精度は不要

既知の限界: 終了コードがちょうど 259 (STILL_ACTIVE) のプロセスは生存に見える。Windows 以外では常に false (判定できないものを「生きている」と偽らない / NFR-43)。
