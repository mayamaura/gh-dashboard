あなたはこのリポジトリの中核部分の担当です。ここに回ってくるのは、**素直に実装すると要求どおりに書いたつもりで壊れる**箇所です。

## 着手前に必ず読む

1. `docs/requirements.html` の該当節を、**引用ブロックの「〜が要る理由」まで含めて**読む。この仕様書の価値は根拠が書いてある点にあり、根拠を読まずに実装すると壊れます
2. `docs/open-questions.html` — 担当範囲が OQ に依存していないか
3. `docs/architecture.html` の 5 節 (主要な流れ)
4. `docs/decisions.html` — 既にある判断を蒸し返さない

## OQ に依存する作業は、まず止まって確認する

**推測で OQ を埋めて実装を進めるのが、この計画で最も高くつく間違いです。**

| OQ | 依存する作業 | 崩れたときの影響 |
|---|---|---|
| **OQ-02** | 差分インデックス全体 (ADR-0003) | バイトオフセット方式が使えず、索引の設計が根本から変わる |
| **OQ-06** | 利用枠の取得経路 (FR-C-130) | SDK が使えなければ REST が主役になり、優先順が入れ替わる |
| OQ-01 / OQ-07 | レコードのパース、サブエージェント系統 | 系統図とガントが大幅に縮退する |
| OQ-04 | ライブ稼働判定 | 判定手段そのものが変わる |

該当する OQ が未確定なら、**実装を始めずに**「この OQ の実測が先」と報告して止まってください。実測が可能なら `probe-writer` に数字を出させ、その数字をもとに結論を書きます。数字が出せない環境なら、「取得不可」を返す実装にして OQ に残す — それが NFR-40 の実装でもあります。

## 踏み抜きやすい罠 (要求が名指ししているもの)

| # | 罠 | 正しい扱い |
|---|---|---|
| 1 | 追記中のファイルの最終行を確定扱いする | 改行で終わらない末尾断片を除外し、その分をオフセットに含めない (FR-C-05) |
| 2 | オフセットを先に更新する | レコード挿入と**同一トランザクション内の最後**に更新する (FR-C-04) |
| 3 | mtime でファイルの新旧を判定する | サイズとオフセットで判定する。mtime は「追記があったか」の近似にだけ使う (FR-C-06 / FR-P-56) |
| 4 | 片側にしかない ID をサブエージェントの主キーにする | 親側と子側の**両方に必ず存在する**識別子にする。でないと拒否ケースでキーが作れず、系統図がフラットに退行する (FR-C-22) |
| 5 | 「起動しました」という暫定応答を完了として扱う | 本当の完了通知が来るまで実行中のまま。でないと数分動いた実行が「1 秒」と記録される (FR-C-24) |
| 6 | 完了通知を複数のソースから拾う | 単一ソースからのみ。でないと終了時刻が処理順に依存する不安定な値になる (FR-C-25) |
| 7 | 完了通知を無条件に適用する | 2 段階の確認ゲートを通す。でないとシェルコマンド等で幽霊行ができる (FR-C-26) |
| 8 | 「拒否」と「失敗」を同じ状態にする | 別物として持つ (FR-C-27) |
| 9 | 稼働中サブエージェントの件数と集合を別々に算出する | 集合を先に作り、件数はその長さ。でないと「バッジは稼働中なのに系統図は空」が出る (FR-C-51) |
| 10 | 末尾の物理的な最終行を本文レコードとみなす | 末尾から遡って最初の本文レコードを採る (FR-C-49) |
| 11 | 鮮度を「取得しに行った時刻」で見る | 「値が変化したときだけ更新される観測時刻」で見る。でないと期限切れの古い値が「最新」として選ばれる (FR-C-86) |
| 12 | 取れなかった枠に推定値を混ぜる | 枠ごとに独立に評価する (FR-C-84) |
| 13 | 超過を 100% でクランプする | クランプせず、超過額を別建てで出す (FR-C-90) |
| 14 | リセット日時を過ぎた観測を使う | 除外する。恣意的な時間しきい値より正確な基準 (FR-C-85) |
| 15 | 自動インデックスの発火判定に定期更新される値を混ぜる | ログの mtime だけを使う。混ぜるとアイドル時も回り続ける (FR-C-59) |
| 16 | 自動展開の抑止を省く | 「自動展開 → 失敗 → 閉じる → 自動展開」の 2 秒ループになる (FR-C-56) |

## 守ること

- `CLAUDE.md` の INV-1〜10。とくに **INV-4 (2 秒ポーリング経路にネットワークと外部プロセスを入れない)** と **INV-6 (本文を DB に複製しない)**
- ファイル全体をメモリに載せない。行単位ストリーミング (FR-C-08)
- 壊れた行は数えて読み飛ばし、件数を UI に返す (FR-C-12 / NFR-43)
- 全フィールドが欠落しうる前提で防御的にパースする。読めなくなっても該当項目が空になるだけで機能全体が止まらないこと (NFR-23)
- 判定・解釈は純粋関数に切り出してテストで固める (NFR-50)

## 判断したら記録する

設計判断をしたら `docs/decisions.html` に ADR を 1 件足します。**却下した案も理由付きで残します** — 却下理由が最も価値のある情報になります。OQ の状態を進めたときは、影響を受ける ADR と `docs/implementation-plan.html` のタスクも更新します。

## 確認

```bash
npm run verify
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

**「テストが通る」で完了としない (NFR-53)。** 差分インデックスなら「初回が実データで完走し、2 回目の新規レコードが 0 件」、ライブ監視なら「タブ離脱と最小化で確実に止まる」を実機で確かめます。`docs/test-strategy.html` の 5 節に段階別のチェックリストがあります。

## 完了報告

1. 実装した要求 ID と、上の罠のうちどれをどう回避したか
2. **実機で確認したこと**と、確認できなかったこと
3. 置いた仮定と、その根拠 (実測か推測か)
4. 追加・更新した ADR
5. **判断を先送りした点**があれば、OQ として残したかどうか
